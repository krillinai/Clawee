# 客户端本地接入 DWS 优化适配初版方案

> 状态：初版讨论稿，方向待确认，尚未实现。
>
> 范围：优先服务个人用户，仅处理 Clawee 客户端对钉钉 DWS 的本地接入；飞书、企业微信和 Gateway 集中治理暂不展开。

## 1. 目标

让用户安装并授权 DWS 后，可直接在 Clawee 中用自然语言使用钉钉能力，不需要自己记忆 DWS 命令。

初版遵循最小成本原则：

- DWS 负责钉钉授权、账号、命令和 API 调用。
- DWS 官方 Skills 负责教 Agent 如何正确使用命令。
- Clawee 只补齐检测、Skill 安装路径和使用引导，不重新实现钉钉能力。

## 2. 初版核心方案

### 2.1 直接使用本机 DWS

Clawee Runtime 沿用现有命令执行能力调用 `dws`，不新增 DWS 命令代理层，不在 daemon 内重新封装通讯录、日历、文档等 API。

客户端只需检测：

- 本机是否能执行 `dws`。
- DWS 版本是否满足官方 Skill 要求。
- 是否已完成 DWS 授权。
- 当前可用的钉钉账号或组织。

检测优先使用 DWS 的 JSON 输出和只读状态命令，不解析面向人的表格文本。调用使用参数数组而不是拼接 shell 字符串。

### 2.2 复用 DWS 官方 Skills

不自己重写钉钉 Skills。初版直接使用 `DingTalk-Real-AI/dingtalk-workspace-cli` 仓库中的 `skills/multi/dingtalk-*` 官方 Skills。

Skill 必须安装到 Clawee 实际管理的 `CODEX_HOME/skills`，不假设用户终端中的全局 Skill 目录会被 Clawee 读取。安装复用现有 Skill 市场和写入、备份、冲突处理能力。

初版建议接入完整的 DWS multi Skill 集合，包括共享依赖 `dingtalk-shared`。这样能优先保留 DWS 的完整能力，也避免 Clawee 额外维护一份能力白名单。

Skill 版本应锁定到明确的 DWS release 或 commit，不在每次安装时直接跟随 `main`。更新先随 Clawee 版本验证，暂不做独立的自动更新系统。

### 2.3 在现有“插件”设置中增加 DWS 状态

不新建单独的连接器中心。在客户端现有“设置 -> 插件”页增加一个“钉钉 DWS”区块，仅展示四项信息：

| 项目 | 可能状态 | 主要操作 |
| --- | --- | --- |
| DWS | 未检测到 / 已就绪 / 版本过低 | 查看安装指引或重新检测 |
| 钉钉授权 | 未授权 / 已授权 / 状态无法确认 | 查看授权指引 |
| 当前账号 | 未知 / 组织与用户 | 查看已登录账号 |
| DWS Skills | 未安装 / 部分安装 / 已就绪 | 安装或更新官方 Skills |

“钉钉登录 Clawee”和“DWS 业务授权”是两套独立能力，界面上不得合并为同一登录状态。

### 2.4 保留 DWS 原有的账号模型

多组织、多账号仍由 DWS profile 管理。初版不在 Clawee 内再建一套账号存储，也不复制 DWS token。

Agent 使用明确的 `--profile` 执行命令，尽量不依赖持久切换全局默认账号。用户有多个可用账号且意图不明确时，先询问用户，不自动选择。

## 3. 需要修改的项目位置

- `client/apps/daemon`：增加轻量 DWS 检测服务和只读 API；不保存 DWS 凭据，不代理具体钉钉业务命令。
- `client/packages/protocol`：增加 DWS 状态、账号摘要和检测错误的最小协议类型。
- `client/packages/skill-market`：将 DWS 官方 multi Skills 作为受控来源加入目录，锁定来源版本并保留上游信息。
- `client/apps/web`：在现有插件设置页展示状态、安装引导和 Skill 安装操作。
- `client/apps/desktop`：初版不增加专用 IPC；如实际验证发现图形应用的 `PATH` 无法找到用户已安装的 `dws`，再增加一个本地可执行文件选择项。

## 4. 初版不做

- 不将 DWS 打包进 Clawee，不自建 DWS 下载、签名校验、更新和回滚系统。
- 不把 DWS token 同步到 Gateway，不读取或展示 token。
- 不封装一套 Clawee 专用的钉钉 API 或 MCP Server。
- 不重写 DWS 官方 Skills，不在 Clawee 中复制命令 Schema。
- 不做跨设备的 DWS 账号同步。
- 不做飞书、企业微信的通用连接器抽象。
- 不新建独立的 DWS 审批引擎或企业级审计链路。

## 5. 写操作的初版处理

DWS 官方 Skills 已包含风险分级、`--dry-run` 和确认规则。初版先复用这些规则和 Clawee 现有 Runtime 审批交互，不另建 DWS 写操作代理。

但这不应宣称为“不可绕过的强制门禁”：当 Runtime 允许无审批执行本地命令时，Agent 仍可直接调用 `dws`。如后续需要强制级保护，再单独设计受控执行入口和命令限制，不在本期提前引入这项复杂度。

## 6. 实施顺序与验收

1. 接入 DWS 官方 Skills，确认 Clawee Runtime 能正确发现。
2. 增加 DWS 及授权状态检测，在插件设置页展示结果。
3. 用真实账号验证自然语言调用，优先覆盖查日程、搜文档、查联系人和查待办。
4. 再验证一项写操作，例如创建待办，确认操作前会展示目标账号和关键参数。

初版验收标准：

- DWS 已安装并授权时，用户无需手写 CLI 命令即可完成上述任务。
- DWS 未安装、版本过低、未授权或 Skill 不完整时，界面能明确指出问题，不把不同问题统一显示为“连接失败”。
- 多账号场景不会静默使用错误的组织或用户。
- DWS 凭据不进入 Clawee 日志、诊断包、本地数据库或 Gateway。

## 7. 待确认方向

1. 初版是否接入 DWS 全部 multi Skills，还是只接入联系人、日历、文档和待办四类能力及 `dingtalk-shared`。为优先保留能力，本文倾向全部接入。
2. 初版是否只提供 DWS 安装和授权指引，由用户在终端完成；本文倾向如此，以避免过早引入跨平台下载、升级和长时授权进程管理。
3. 是否接受初版的写操作确认属于 Agent 交互约定，而非 Clawee 强制安全边界。如不接受，则必须扩大范围设计 DWS 受控执行层。
