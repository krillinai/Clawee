# P8 客户端网络与 Runtime 异常自动上报方案设计

日期：2026-10-15。状态：首版已实现并验证；测试阶段补充员工归属、技术上下文与原始日志附件，验证结果以本次执行记录为准；尚未正式发布。

## 1. 目标与边界

用户无需导出诊断包。客户端自动向当前配置的 Gateway 自己的反馈中心上报必要的技术异常，由该部署的授权人员通过后台人工查看、确认和处理。

本期只交付三个能力：异常采集、可靠且有界的自动上报、现有反馈后台中的查看与人工处理。不建设日志平台，不做自动巡查、定时巡检任务、告警推送、智能归因或自动修复。

覆盖桌面客户端的两个实际场景：

1. 任务中出现“Codex 响应连接中断，正在自动重连”，但同电脑上独立 Codex 使用相同模型正常。
2. 登录页面停留在“正在等待本地 Runtime，连接恢复后即可继续登录”，用户无法登录或配置服务器。

第二类异常可能发生在 daemon 未启动、尚未登录、没有任务或会话时，必须能够独立采集和上报。不得把用户登录、daemon 正常运行或 `thread_id` 存在作为前提。

本期自动上报以 Electron 桌面入口为范围；共享 Web 补充桌面连接异常观测。独立浏览器入口保留现有本地诊断行为，本期不另建浏览器离线上报机制。本文不修改任务执行、超时和重试策略，也不自动读取独立 Codex 的配置、凭据或日志。

## 2. 复用现状与总体结构

接收方为客户端当前配置的企业 Gateway 自己的反馈中心，不再使用固定维护方地址，也不在失败时回退其他部署。不携带客户登录 Token 或模型 API Key；异常写入凭证只授权该记录。未配置或无法校验 Gateway 时不上报。

桌面自动异常、客户端手工反馈及其附件和状态查询均绑定目标 Gateway；管理台手工反馈直接调用本部署反馈服务入库，不通过 HTTP 转发。各部署分别保存记录、材料、处理结论与审计。

现有手工反馈具有会话依赖、用户确认、材料上传等流程，不适合直接改造成自动上报。保留原流程，新增轻量 JSON 异常入口；后台列表、权限、处理状态和审计复用现有反馈中心。

```text
桌面启动状态、daemon 生命周期 -----------+
daemon 内的 Runtime / 模型异常 --已有进程消息--+--> 桌面主进程中的唯一上报器
Web 的本地连接异常 ----------受限 Bridge--+      | 本地有界队列
                                               v
                                  A2A 现有反馈模块 / 数据库
                                               v
                                  后台列表、详情、人工确认处理
```

- daemon 已通过 Electron `parentPort` 向桌面传递子进程与性能消息，本期扩展同一通道传递结构化异常，不新增本地网络服务或共享数据库。
- 桌面主进程在启动 daemon 之前初始化上报器，统一分配安装标识、合并异常、持久化和上传。daemon 或渲染页面失效时，上报器仍可工作。
- daemon 只发送观测事实；Web 只发送白名单连接状态和请求失败摘要。最终字段校验、脱敏和发送由主进程负责。
- 测试阶段附带首次故障时的有界原始技术日志快照，不截屏，不修改 Codex 内核，不抓包。Runtime 未暴露的网络阶段和状态码明确记为未知。

## 3. 采集触发与恢复判断

| 链路 / 场景 | 触发条件 | 主要证据与采集入口 |
| --- | --- | --- |
| 桌面启动与本地服务 | Runtime 解析、校验、探测或 daemon 启动明确失败；daemon 非预期退出 | `bootstrap-controller.ts`、`daemon-manager.ts` 的阶段、错误码、退出码和退出信号 |
| 启动长期等待 | 启动或自动恢复开始后 60 秒仍未就绪 | 主进程记录 `RUNTIME_STARTUP_STALLED`，附最后阶段和已等待时长；只观测，不中止启动 |
| Web 到 daemon | 已就绪后的断连持续 15 秒；本地请求超时、连接失败、事件流异常结束 | 现有连接服务、事件订阅错误处理；经 Bridge 传至主进程 |
| daemon 到 Codex | app-server 启动、初始化、通信、执行超时或异常退出 | app-server host / runner 和运行管理器中的原始结构化错误 |
| Codex 到模型接口 | Runtime 上报可重试错误、重连、响应流中断、模型请求超时或 HTTP 错误 | 在 `onNotification` 收到原始 `error` 时采集，不能只使用前端归一化后的中文提示 |

规则：

- 明确错误立即入队；60 秒与 15 秒仅用于识别没有明确报错的持续等待。正常首次加载不立即报错。
- 数据迁移、用户主动停止、正常退出、用户取消任务、更新期间主动关闭 Runtime 不上报为故障；阶段明确失败仍应采集。
- 主进程监测真实启动阶段，不以“登录页出现等待文案”直接判定根因。若启动已就绪但 Web 无法连接，由 Web 连接状态补充识别。
- 连接恢复、启动就绪或模型再次输出有效响应后更新恢复状态；工具仍在执行不代表模型连接恢复。
- 任务结束另记录成功、失败、取消或中断。没有观察到恢复时标记未知，不能把“没有后续错误”当成恢复。
- 截图中的等待场景必须在未登录、无会话、daemon 完全启动失败时通过验收。

## 4. 最小数据契约

在 `client/packages/protocol` 新增自动异常协议，与手工反馈 DTO 分开。首版 `schema_version=1`，严格白名单，不接受任意 `raw`、日志数组或请求对象。

| 字段组 | 必要字段与约束 |
| --- | --- |
| 标识 | `incident_id`、`installation_id`、`app_session_id`：随机 UUID；`revision`：主进程递增整数 |
| 关联 | 可选 `run_id`、`thread_id`；启动异常仅关联本次启动尝试，不伪造任务或用户 |
| 定位 | `source`：desktop / daemon / web；`layer`：desktop_bootstrap / web_daemon / daemon_codex / codex_model；`stage`、`error_code`、可用的底层 `transport_code` |
| 错误事实 | `message`：脱敏技术错误摘要，最多 1 KB；可选 HTTP 状态码、退出码、退出信号、上游请求标识；无法取得时省略 |
| 时间与影响 | 首次、最后发生时间，发生次数、重试次数、阶段耗时、首次报错前无响应时长；`outcome`：ongoing / recovered / failed / unknown；任务结果单独保存 |
| 环境 | Clawee / daemon / Runtime / Electron 版本、构建 SHA、系统与架构；未启动的组件版本可为未知 |
| 对照配置 | 模型名、接口指纹、已知协议和传输方式、实际生效且可读的超时 / 重试配置、代理变量是否设置；不可读字段为未知，不把文档默认值冒充实际值 |
| 员工归属 | 可选 `reporter`：企业 origin 指纹、稳定账号 ID、姓名快照、Agent ID；按发生时账号归属，接收中心标为客户端快照而非可信认证身份 |
| 技术上下文 | `diagnostics`：错误类型、文案最多 2 KB、堆栈最多 4 KB、cause 错误码、请求方法与不含查询参数的路径；`timeline` 最多保留最近 20 条异常、恢复及结束事件 |
| 原始日志 | `logs_expected` 表示是否成功采集附件；通过独立日志接口上传，不把日志正文塞进异常 JSON |

接口指纹由规范化后的模型 Base URL 的 origin 和路径计算 SHA-256，排除用户名、密码、查询参数与片段；不上报明文 URL。代理仅记录是否设置相关变量，不发送值，也不声称已识别系统代理或实际路由。

`message` 仍由错误码、传输码与 HTTP 状态拼接。测试阶段通过独立的 `diagnostics` 与日志附件保留技术错误文案、内部路径及调用位置，不再将它们全部压成错误码；只过滤明确凭据，不额外匿名化员工姓名或内部路径。不得原样转发 `params`、`additionalDetails`、整个异常对象；`additionalDetails` 仅提取白名单技术片段并脱敏、限长，遇到请求/响应正文标记即停止提取。不主动读取 Prompt、模型回答、命令与工具输入输出、业务文件正文、截图或硬件指纹。技术日志自身可能含有内部业务上下文，应按内部测试材料使用；正式上线前另做脱敏和权限复核。

保留 Runtime 错误分类与可用 HTTP 状态，不能再次统一压缩成“网络异常”。同电脑同模型正常只是一条对照线索，不构成已确认根因。

## 5. 客户端合并、队列与发送

### 5.1 合并规则

- 同一应用会话、同一启动尝试或 Run、同一链路和错误分类合并为一个 `incident_id`，累计次数，保留首条及最近一条安全错误摘要。
- 不用整段错误文案作为合并键；优先以结构化错误分类区分，例如 HTTP 503 与连接超时不能因为中文文案相同而合并。
- 首次立即调度发送；持续发生时最多每 60 秒更新一次；恢复、最终失败或任务结束时立即调度最后状态。
- daemon / Web 事件带源事件标识，主进程避免同一事件重复计数。不同链路可各留一条，通过启动尝试或 Run 关联，不做跨组件自动根因推理。
- 采集器和上报请求自身的失败只写本地限频日志，禁止递归上报。

### 5.2 唯一持久化队列

由桌面主进程维护用户数据目录中的 `auto-incidents.json`，使用串行写入和临时文件原子替换，沿用现有 settings 文件持久化方式。无需给 Electron 增加 SQLite 原生依赖，也不挪用手工反馈草稿表。

每条本地记录保存异常快照、版本、已确认版本、写入凭证和下次发送时间。凭证不进入诊断 payload 或业务日志，文件仅允许当前用户访问。

- 队列上限 100 条，单条异常 JSON 不超过 32 KB，独立日志附件不超过 256 KB，最长保存 7 天。先清理已发送且结束的记录，再淘汰最旧记录；淘汰数量仅记本地限频日志。
- 已发送但尚未结束的异常保留合并状态；后续恢复可使用同一 ID 更新。应用重启后未结束的旧记录标记 unknown，不伪造恢复。
- 每次只发送一条，单次请求超时 5 秒。失败后按 30 秒、2 分钟、10 分钟、之后每 30 分钟重试；遵循服务端 `Retry-After`。
- 网络错误、超时、429、5xx 可重试；400 / 413 停止该条发送，401 / 403 按错误码停止无效凭证或被禁止的上传。404 / 405 视为接收端未升级，本次应用会话暂停发送，下次启动再试。
- 只清除服务端已确认的版本；发送期间出现新版本不能被旧响应覆盖或误删。关闭应用不等待上传完成，下次启动补传。

这是有界、尽力的技术异常采集，不承诺零丢失；主进程崩溃、整机断电和磁盘不可写时不能保证最后事件已落盘，不增加第二个守护程序。

### 5.3 告知与企业策略

- 标准客户端默认开启轻量技术异常上报，并在首次启动提供明确告知，说明接收方与数据范围；不为每次异常弹确认框。
- 本地“自动上报技术异常”开关必须在系统菜单也可关闭，不依赖登录或 Runtime 启动成功。关闭后停止采集与发送并清理待传队列，不影响手工反馈。
- 接收策略由当前 Gateway 的 `feedback.enabled` 控制。`feedback.admin_ui_enabled` 只控制管理台入口；原 `external_feedback_allowed` 保留兼容，不再控制本部署反馈，不能将其解释为允许跨部署外传。
- 主进程独立查询无需登录的 `GET /api/v1/feedback/policy`，返回接收开关、政策版本及有效期；在启动 daemon 前初始化，查询不阻塞启动。每分钟刷新，缓存有效期最多一小时；无有效策略时仅本地暂存，恢复后补传。已知禁止立即停止采集与发送。
- 告知绑定目标 Gateway 和告知版本，接收方变化后重新告知；快照、日志、手工草稿及凭证绑定创建时的目标，不因切换后台改投。配置无效时不能降级为其他目标；继续禁止 HTTP 重定向。
- 升级前的固定维护中心异常队列停止补传并清理，旧手工草稿仅本地查看或导出，需要新建反馈重新确认目标。历史已入库资料不跨部署迁移。
- 不伪造手工反馈的 `confirmed` 或 `consent_at`。新通道使用独立的自动异常政策版本标识。

## 6. A2A 接口与存储

### 6.1 单个 JSON 接口

新增 `PUT /api/v1/feedback/incidents/:incidentId`，使用第 4 节完整快照，不走附件、manifest、分片和对象存储流程。

`GET /api/v1/feedback/policy` 在反馈中心关闭时仍可查询并返回 `enabled=false`，不依赖后台页面展示或用户会话。反馈中心关闭时不挂载写入接口，公开策略查询不能授权读取事件或修改人工状态。

- 首次由主进程生成该事件专属的 32 字节随机写入凭证，通过 `Authorization: Bearer` 发送。服务端只保存哈希，后续更新校验同一凭证。
- 首次创建无需客户账号登录；公开创建不等于可信身份。复用现有反馈入口的代理识别、来源校验与 IP 限流，不在客户端内嵌公共管理员密钥。
- 可用时沿用现有可信部署来源；无凭证时明确标记“匿名 / 自报”。安装 ID 和自报客户名称不能作为可信身份或限流的唯一依据。
- 接口只允许写入白名单技术字段，不能读取事件、枚举安装设备、改处理人或处理状态。读取与人工操作仍走后台鉴权和现有 RBAC。
- 使用事务按 ID 幂等更新：相同版本且内容相同直接确认；相同版本不同内容返回 409；更旧版本不回退数据，返回当前已接收版本；新版本更新技术事实。
- 响应包含 `incident_id`、`accepted_revision`。首次 201，重复或更新 200；参数、大小、授权和限流分别返回明确的 400 / 413 / 403 / 429 错误码。
- 沿用现有反馈模块服务端 IP 限流，并为安装标识增加每日最多 100 条新增异常的容量保护。写入凭证只授权更新本条记录，不授予读取权限。
- 拒绝未知字段、不支持的协议版本和重定向；服务端再做字段校验、敏感信息检查，接口请求正文和 Authorization 不写访问日志。

### 6.2 复用反馈记录

复用 `feedback_reports` 的 JSON 数据结构，新增 `kind=automatic_incident` 和专用结构化诊断字段；历史未设置 kind 的记录视为 `manual`。

- 自动异常没有附件与 manifest，不占手工材料上传状态机；通过校验后可直接供后台查看，现有 ready / normal 等可见性状态按实际含义设置，不伪造用户确认或附件上传。
- 技术快照版本与后台人工处理的乐观锁版本分开。上传不得覆盖人工结论、处理人、处理状态或处理操作版本，不因一次恢复而自动标记已处理。
- 保留现有人工操作审计；每次计数更新不追加一条工单流转事件，避免无意义膨胀。
- 中心按首次接收时间保留 30 天，复用现有清理任务；重复上传不无限续期。JSON 元数据也必须受现有中心容量检查约束，不能因为没有附件就绕过配额。
- 筛选需要的索引通过 `server/db/migrations` 增加，不手工修改运行库；不新增数据库、消息队列或日志检索服务。
- 现有手工反馈 API、权限、历史记录不变。自动异常不接入现有反馈 MCP 的自动读取 / 处理流程，本期由人工使用后台处理。

## 7. 后台页面与人工巡查

复用 `server/web/src/pages/feedback.tsx`，不增加独立管理台。

- 列表增加“手工反馈 / 自动异常”筛选。自动异常显示来源或安装 ID 后缀、链路与错误摘要、首次 / 最后发生时间、次数、恢复状态、App / Runtime 版本、人工处理状态。
- 沿用现有来源、时间、版本和状态筛选，补链路及错误类型筛选；按最后发生时间倒序，便于人工看近期问题。不新增趋势图和复杂统计。
- 自动异常详情展示员工账号快照、版本、配置指纹、阶段、错误原因、调用位置与恢复时间线；收到日志后提供读取和下载，不显示不存在的会话入口；未知字段显示“未知”。列表增加员工姓名或稳定账号 ID 筛选。
- “运行已恢复”和“人工已处理”分开显示。处理沿用“待处理 / 处理中 / 已处理”，由人员查看证据、填写结论后确认。
- 内部近期定期人工打开后台，优先检查最终失败、持续等待及重复发生记录，再按来源和版本对照。没有定时巡查程序、自动确认、告警推送或自动派单。
- 页面实现遵循 `docs/design/design.md` 和 `docs/frontend/frontend-development-guidelines.md`；查询失败要显示错误，不得以空列表掩盖。

对本次客户问题，人工使用上报中的 Runtime 版本、模型名、接口指纹、已知代理 / 协议配置与正常的独立 Codex 做对照，再决定修复。未获取的配置由内部协助确认，不能把“同样模型”理解成整条请求链路相同。

## 8. 开发落点与顺序

| 顺序 | 落点 | 交付与验证 |
| --- | --- | --- |

## 11. 测试阶段诊断增强

本节补充员工归属与日志附件，取代首版仅上报错误码摘要的限制，不改变手工反馈的独立采集流程。

- 企业会话通过现有 daemon 进程消息向主进程同步稳定账号 ID、姓名和 Agent，不传登录 Token。主进程仅采用尚未过期且企业指纹匹配的账号快照；登出、账号切换和 daemon 退出后清除当前身份。旧记录不按新账号补贴身份，登录前失败仍可独立上报。接收中心尚未核验跨 Gateway 员工身份，后台明确显示“客户端快照”，不能将其用于认证或授权。
- 同一错误进一步按发生时员工和失败请求的方法、路径分组，避免把不同员工或不同接口的问题合在一起。路径不带查询参数；错误文案最多 2 KB，调用栈最多 4 KB，时间线最多 20 条。
- 每条新异常首次发生时读取 `desktop-main.log`、轮转文件 `.1`，有 Run 时额外读取 `runs/<run_id>/stderr.redacted.log`。只读这些固定技术日志，不扫描工作区、会话文件或整个 Runtime 目录。各文件最多读取尾部 64 KB，整份 NDJSON 附件最多 256 KB；`content` 保留日志实际技术内容，逐源记录 `missing`、`truncated` 和原文件大小，不冒充完整历史日志。
- 本地附件保存在用户数据目录的 `incident-logs/<incident_id>.ndjson`，目录权限 0700、文件权限 0600。摘要确认后通过 `PUT /api/v1/feedback/incidents/:incidentId/logs` 独立上传，使用同一条异常的随机写入凭证及 `X-Content-SHA256`。收到服务端确认后删除本地附件；本地关闭、企业禁止或队列淘汰时也删除。切换后台不把旧记录或附件改投新后台，仅在返回原后台且策略允许时继续补传。未完成附件可在 7 天内重启补传。

## 12. 模型检测中的网络诊断（增量方案）

定位为**当前模型链路的按需诊断**，不是全设备网络体检。第 1 节的自动采集与上报范围不变。第一步及检测失败上报已开发：增强现有检测的网络错误分类、可观察阶段与本地结果展示，仍只发一次模型请求，沿用 20 秒总超时；当前生效配置检测失败时复用现有自动异常队列。Runtime 对照检测保留为后续增量。

### 12.1 改造前的能力与缺口

- “检测模型”已由 daemon 向配置的模型接口发送最小流式请求，并非只检查配置格式；已有 20 秒超时、HTTP 错误分类和首段有效文本判断。
- 缺口是网络异常被统一为“连接失败”，无法区分域名解析、连接、证书或流中断；现有超时也未区分等待响应头与等待模型文本。
- 该请求不经过 Codex Runtime。项目另有 Runtime 检测能力，因此“检测模型成功”不能证明 Runtime 的模型链路正常。

### 12.2 最小方案

保留现有“检测模型”入口，不新增网络诊断页面，按以下顺序推进：

| 能力 | 最小做法 | 能回答的问题 |
| --- | --- | --- |
| 增强现有检测，已实现 | 保留可识别的底层错误及 cause 错误码；记录是否收到响应头、是否收到有效模型文本和总耗时 | 请求失败在什么可观察阶段？更像网络、认证、限流还是接口问题？ |
| 补充 Runtime 对照检测 | 直连检测成功但任务仍异常时，在同一区域提供“检测 Runtime 链路”，复用已有 Runtime 探测 | daemon 能访问模型，但 Runtime 是否也能完成一次最小请求？ |

第一步不额外发请求，不单独实现 DNS、TCP、TLS 探针。直接从真实请求的错误中识别域名解析失败、连接拒绝、证书校验失败、连接重置等；没有明确证据时保留“连接失败，原因未知”。

检测结果只给**事实、可能原因、下一步**，不做智能归因：

| 观测事实 | 展示判断与建议 |
| --- | --- |
| 域名解析或证书校验明确失败 | 展示具体分类，建议检查 Base URL、DNS 或企业证书配置；不关闭证书校验 |
| 未收到响应头便超时 | 显示“等待接口响应超时”；可能涉及连接、代理或上游，不直接断言断网 |
| 收到 HTTP 401 / 403 / 429 / 5xx | 分别提示认证、权限、限流或上游错误，不统称网络故障 |
| 收到成功响应头，但未收到有效模型文本便超时或流异常结束 | 显示“模型文本等待超时”或“响应流异常结束”；仅有明确传输错误时判为连接中断 |
| daemon 检测成功，Runtime 检测失败 | 提示重点对照 Runtime 错误、代理与运行配置；不能据此确认代理就是根因 |
| 两项检测均成功，任务仍异常 | 说明本次短请求正常，不能排除偶发故障或长连接问题；结合原任务异常与日志分析 |

Runtime 对照只使用已保存且当前生效的配置，不保存待检测草稿，不修改用户配置；配置不一致的两次结果不作对照。它会产生额外模型请求，可能计费，执行前明确说明。

### 12.3 与自动上报的关系及边界

- **主动检测由用户点击触发**；任务异常仍按前文被动采集，不因每次重连追加模型请求，不新增后台轮询或定时检测。第二步按需执行，不让正常检测默认承担两次模型调用。
- 检测结果先在本地展示。仅当前生效配置的检测失败在策略允许时复用现有异常上报链路，以 `model_check.*` 阶段和“手动模型检测”上下文区分；未保存草稿、成功结果及检测期间登出或切换配置后的旧结果不上报。同一接口与模型的重复错误沿用队列合并，不关联虚假的任务，也不把手动检测成功当作真实任务恢复。
- 上报只补充检测来源、时间、配置指纹、可观察阶段、错误码、HTTP 状态及耗时；不上传 API Key、代理地址、明文 Base URL 或测试回答，不新建日志或工单系统。
- daemon 不可用时，模型检测本身无法执行，沿用启动异常与本地连接提示，不用模型网络检测替代 Runtime 启动诊断。探测失败不影响已保存配置或任务重试策略。
- 首期不做测速、公共网站连通性测试、Ping、路由追踪、抓包、全量代理发现、自动切换网络或自动修复；也不据一次成功承诺长连接稳定。

**实施方向：现有入口增强、真实请求错误分类、Runtime 按需对照、复用异常上报。本次完成第一步及检测失败上报；后续按需复用现有能力，不扩展成独立网络诊断系统。**

## 13. 模型重试的原因与提示

- daemon 统一解析 Runtime 错误，客户端提示与自动上报共用分类。优先使用结构化类型和 HTTP 状态，再从错误文案和白名单技术片段补充连接错误、请求标识；兼容 Rust/Windows 常见错误表述。没有证据时明确“具体原因未返回”，不推断客户网络或代理故障。
- 同一 Run 的模型响应错误使用同一异常记录；`first_message`、`first_diagnostics` 固定保留首次证据，现有顶层字段和 `diagnostics` 更新最近错误，沿用时间线与最终任务结果。其他启动、Web 连接与手动检测异常仍按原分类合并。日志附件仍只保留首次快照，不增加采集次数或新接口。
- 客户端仅在展示层合并同一次连续重试，不删除持久化原始事件。模型文本恢复后结束当前重试；失败、取消和结束未确认恢复分别展示，不遗留“正在重试”。次数仅展示 Runtime 明确提供的进度。失败提示包含最后已知原因和建议，可展开技术详情并复制 Run 排查编号；不假称上传成功。
- 后台详情分别展示首次和最近错误、技术片段及请求标识；列表不暴露这两份技术诊断。先查看已有证据，再用请求标识或时间、模型、接口指纹对照现有中转/上游日志。上游未提供的内部原因仍需上游日志确认。
- 发布顺序：先升级 Gateway 和管理台，再升级客户端。本次增加可选诊断字段及模型响应记录的更新规则，旧 Gateway 可能拒绝新字段；不增加兼容协商或备用上报通道。不改 Runtime 重试策略，不引入抓包、自动探测或新日志平台。
