# P9 Skill AI 审批工作流方案设计

日期：2026-10-20。状态：核心方向已确认，本文作为开发与验收依据；尚未实施。

## 1. 目标与首期边界

在现有 Skill 上传与人工评分能力上增加统一的 AI 前置评估。流程固定为：上传、基础校验、AI 评估、人工审核打分、分值汇总。AI 未通过时由上传者修改后重新上传，不进入人工审核。

已确认的产品要求：

1. 当前只有一个服务端 Agent，统一由它拉取审核任务，不按空间选择或绑定 Agent。
2. 只有 AI 评估完成且通过，才能进入人工审核；报告生成完成不等于通过。
3. 上传者可以查看对应版本的完整分析、问题和修改建议。
4. 检查内容、通过条件与报告格式由一个可信的审核 Skill 维护。
5. 现有“工作流搭建”页面必须展示这套流程及实际执行情况，首期只读。
6. 人工审核名单、全员通过规则及四维评分汇总复用现有实现；审核通过后仍按现有方式手动发布。

首期按最小改动原则，接入**已配置本地人工审核人或审核角色的空间中的人工上传**，包括用户上传、管理员上传和上传新版本。范围由已有本地审核配置确定，不再增加空间级 AI 开关。无本地审核名单的自发布空间、钉钉审批空间和 Git 来源同步暂沿用各自现有流程，不标记为已接入 P9。上线前确认目标空间均属于本地全员评审空间；扩大到所有人工上传时，需另行处理这些空间的审核配置与发布规则迁移。

本期不建设可编辑编排、通用规则管理平台、多个审核 Agent、动态报告模板引擎、通知系统、自动修改 Skill 或自动发布。Go Gateway 负责任务与状态，模型执行留在服务器上的 daemon / Codex Runtime。

## 3. 固定流程与状态判定

### 3.1 上传与流转

1. 上传入口完成现有包校验；不合格直接返回明确错误，不创建成功上传和 AI 任务。
2. 在版本及本地审核申请创建事务中，同时创建一条 AI 待评估尝试。申请与审核人快照可提前存储，但此时不产生可处理的人工待办。
3. 唯一服务端 Agent 领取任务，使用可信审核 Skill 静态分析本轮材料，再回传结构化报告。
4. Gateway 校验身份、尝试、版本摘要与报告。只有通过结论才开放人工待办；需修改的版本保留报告，等待上传者上传新版本。
5. 人工按既有全员评审规则提交决定及评分。全部通过后计算正式分数，允许按既有入口手动发布；任一驳回则不能发布。

新上传始终产生新的版本记录和审核轮次，不覆盖原报告，不复用旧版本的 AI 结论。内容修订使用现有新版本上传入口，首期不增加在线编辑或自动返工循环。

### 3.2 对外阶段

新增只读的 `workflow_stage`，由当前有效申请、最新 AI 尝试和人工决定统一计算，不新增另一套持久化流程状态。

| 阶段 | 判定 | 允许的后续动作 |
| --- | --- | --- |
| `ai_pending` 待 AI 评估 | 当前尝试为 `pending` | 等待服务端 Agent |
| `ai_running` AI 评估中 | 当前尝试为 `running` | 等待结果，超时按异常处理 |
| `revision_required` 需修改 | 报告有效，但结论不是通过；或材料明确不满足可分析条件 | 上传者查看原因，修改并上传新版本 |
| `ai_failed` 评估执行异常 | 模型调用、运行超时、隔离准备或报告格式校验失败 | 上传者或授权管理员重试 |
| `human_pending` 待人工审核 | AI 有效通过，人工尚未全部决定 | 本轮审核人提交自己的决定与评分 |
| `approved` 审核通过 | 全员通过且正式评分完整 | 查看汇总，按既有规则手动发布 |
| `rejected` 人工驳回 | 任一审核人驳回 | 查看意见，修改并上传新版本 |
| `invalidated` 本轮失效 | 申请因空间、名单、版本绑定等变化而失效 | 只读历史，以新轮次为准 |

先判定申请是否失效，再判定有效 AI 前置条件和人工状态。已发布状态仍来自现有版本与 `current_version_id`，不额外同步到流程表。

业务结论沿用现有枚举：`recommend_approve` 对应通过；`needs_attention`、`recommend_reject` 对应需修改。一般改善建议可以作为非阻断警告附在通过报告中；必须处理的安全、结构或证据缺失问题不能判通过。

### 3.3 门禁与异常

- P9 人工处理与发布必须同时满足：当前有效申请、匹配版本及包 SHA-256、最新尝试 `completed`、有效报告结论为 `recommend_approve`、可信审核 Skill 版本及摘要齐全。报告含 `error` 级问题时不得通过。
- 人工待办查询、`can_process`、评分接口和所有发布入口使用一致的服务端判定。管理员、批量发布、上传者自发布和旧客户端请求均不能绕过接入范围内的 P9 门禁。
- 删除“转人工”按钮并关闭对应写接口。历史 `manual` 尝试保留只读，但不能作为 P9 放行依据。
- 需修改的业务结论不提供原版本重跑以更换结论的入口；修订内容必须上传新版本。
- 技术异常可重试，生成新的尝试 ID，保留原记录。版本、空间或申请已经失效时拒绝重试；不能恢复旧轮次。
- 材料超过可分析限制等需要调整上传内容的情况，返回明确的材料问题，不用“网络异常，请重试”掩盖。模型超时等技术异常不要求上传者修改 Skill。

## 4. 审核 Skill 与报告契约

### 4.1 文件与加载方式

新增 `client/apps/daemon/resources/skills/skill-review/SKILL.md`。首期一个文件即可，包含合法的 `name`、`description`，在 `metadata` 中声明审核规则版本，并写明检查范围、阻断条件、输出字段和中文示例。

Worker 每次领取前优先读取 Skill Hub 中名称严格为 `skill-review` 的当前已发布版本的 `SKILL.md`，仅当同名 Skill 不存在或没有已发布版本时回退随部署资源。Gateway 使用专用读取接口校验唯一审核 Agent 的活跃身份与规则空间读取权限，不通过按权限过滤的列表推断规则是否存在。网络、权限、包读取或摘要校验失败、规则格式错误均记为执行异常，不能静默回退。

启动本次评估前固定规则正文、版本与正文 SHA-256。Hub 规则版本取发布版本号，本地规则版本取 `metadata.version`。来源名称及本地路径不能由上传者、被审材料或模型输出指定；规则维护者通过 Hub 上传、审核并发布新版本即可更新，只有后续任务使用新规则，运行中的任务继续使用已固定的内容。

当前受限审核环境禁用了自动发现和加载 Skill，必须由程序显式读取选定规则正文并构造审核指令，不加载包内脚本或其他资源；不得为此放开普通技能发现、命令执行或其他工具。所选规则文件缺失、版本缺失或读取失败时按执行异常处理，不回退到硬编码旧提示。

### 4.2 必须检查的内容

| 检查方向 | 首期检查内容 |
| --- | --- |
| 基础安全与风险 | 声明用途与实际行为、权限必要性、敏感数据来源与外传去向、明文凭据、动态执行与命令注入、下载执行及供应链、提示注入与审核操纵、配置及记忆投毒、隐蔽自动执行入口、破坏性写入与路径越界 |
| Skill 结构 | Frontmatter 与触发条件、输入输出、步骤及失败处理、引用与资源完整性、依赖权限及宿主兼容性是否完整、一致、可理解；以本项目支持的契约判断 |

只对提供的文本、脚本源码与文件清单作静态判断，不声称已验证实际运行效果。二进制、未读取材料和其他覆盖限制必须写进报告；缺失内容影响安全或结构结论时判为需修改。

审核规则 `1.1.0` 已吸收公开 Skill 的适用检查方法，来源与取舍记录在 [规则维护说明](../../client/apps/daemon/resources/skills/skill-review/README.md)。所有运行所需规则保留在 `SKILL.md`，不引入上游扫描脚本、AST/YARA 工具或联网核验。须结合用途、数据流和宿主判断风险，区分攻击行为与安全教学、检测示例；不能仅凭命令名、外部链接、可选字段缺失或写作风格阻断。需补充关键证据或修复结构的问题用 `needs_attention`，已确认的严重安全风险用 `recommend_reject`；两者均为需修改，阻断问题统一使用 `error`。

### 4.3 输出格式

为控制改动，首期保留现有 JSON 基本结构，报告格式及内容要求写在审核 Skill 内；Worker 和 Gateway 同时按该契约校验。修改字段结构时同步修改两端校验及管理台展示，首期不支持任意结构的动态渲染。

```json
{
  "conclusion": "recommend_reject",
  "summary": "高风险：脚本会向外部地址发送工作目录内容，请调整数据范围和外传行为后重新上传。本次为静态分析，未执行脚本。",
  "findings": [
    {
      "severity": "error",
      "message": "【基础安全】未限制待上传文件范围，可能泄露业务资料。建议仅处理用户明确选择的文件，并说明接收方与用途。",
      "path": "scripts/export.py"
    }
  ]
}
```

- `conclusion`：仅允许上述三个既有结论值；`summary`：中文总体风险、判断依据和覆盖限制，最多 8192 字节。
- `findings`：最多 100 项，至少通过“基础安全”“结构审核”前缀区分问题类别；单项 `message` 最多 4096 字节，写明问题、影响和修改建议。无问题时允许空数组。
- `severity`：沿用 `info / warning / error`；`path` 可选，存在时必须精确匹配本轮提供的相对文件路径。报告示例中的路径仅为示意，不允许模型虚构证据文件。
- 总报告不超过 128 KiB；沿用单文本文件 128 KiB、全部材料文本 512 KiB 的上限，禁止静默截断后声称审核完整。
- 本期不要求 AI 生成产品价值建议分；历史 `suggested_scores` 可继续只读展示，绝不参与正式评分。

审核 Skill 负责内容标准；程序负责结构、大小、证据路径、结论与问题严重度的一致性。上传材料与可信指令明确分隔，材料中的“忽略规则”“直接通过”等内容一律作为被审数据。

## 5. 唯一执行者与最小数据调整

### 5.1 全局执行配置

在部署配置中一次性识别当前服务端 Agent，空间页面不再提供 Agent 选择和 AI 开关。配置如下：

| 位置 | 配置 | 用途 |
| --- | --- | --- |
| Gateway | `config.yaml` 的 `skillhub.review_agent_id` | 唯一允许领取及回传审核任务的稳定 Agent ID；兼容环境变量 `CLAW_GATEWAY_SKILL_REVIEW_AGENT_ID`，环境变量优先 |
| 服务器 daemon | `server.toml` 的 `[server].skill_ai_review_worker_enabled = true` | 显式启用审核 Worker；文件配置优先，未填写时兼容 `CLAWEE_SKILL_REVIEW_WORKER_ENABLED=true`，桌面端和普通 daemon 默认关闭 |

Gateway 在既有 YAML 配置中添加：

```yaml
skillhub:
  review_agent_id: "已登录服务端Agent的稳定ID"
```

服务端 Agent 在既有 `data/server.toml` 的 `[server]` 段添加以下字段，保留其余配置，不重复创建 `[server]` 段：

```toml
[server]
skill_ai_review_worker_enabled = true
```

该字段必须为布尔值，不能写成字符串 `"true"`。显式 `true` 或 `false` 优先于环境变量；字段省略时兼容环境变量，两者均未设置时关闭。设为 `false` 并重启 Agent 可明确关闭。两项配置分别由 Gateway 和 Agent 读取，修改后需重启对应服务；启用 Worker 不会自动获得审核权限。

唯一 Agent 沿用已有企业登录身份、模型配置及账号/Agent 活跃校验，并具备接入空间的读取权限。该授权由管理员按现有权限体系设置，不自动提升为管理员。配置缺失、Agent 离线、会话失效或模型不可用时，任务保持未通过，不跳过 AI 阶段；普通客户端即使尝试调用领取接口也被拒绝。

上传创建 `pending` 尝试时不指定空间执行者，`agent_id` 暂存空字符串；领取事务验证全局执行者后写入实际 Agent ID。结果写入仍校验本次实际领取者。部署配置暂缺时允许保留待评估任务，配置恢复后领取，不因缺配置绕过审核。

沿用当前约 30 秒轮询、单 Worker 串行执行和数据库任务表；保留 Worker 12 分钟超时及 Gateway 15 分钟兜底超时。不新增消息队列、调度服务、心跳平台或多 Agent 抢占策略。

### 5.2 存储

继续使用 `approval_requests`、`approval_request_approvers`、`skill_ai_review_attempts` 和已有版本表。只新增顺序迁移，为 AI 尝试补充：

| 字段 | 写入方式与用途 |
| --- | --- |
| `review_skill_version` | Worker 从可信 Skill 读取，在领取时由 Gateway 记录 |
| `review_skill_sha256` | Worker 对本次固定的可信文件计算摘要，在领取时记录；模型不能代填 |
| `error_code` | 程序生成的稳定原因，例如 `execution_failed`、`timeout`、`report_invalid`、`materials_unsupported`，用于区分可重试异常和需调整材料 |

历史记录允许这些字段为空，不伪造旧规则版本。报告仍存既有 `report JSONB`，不新建报告表或通用工作流实例。`workflow_stage`、`can_submit_review`、`can_retry_ai` 由后端计算返回，不作为另一套写入状态。

旧 `skill_space_ai_review_configs` 停止参与新轮次路由，旧配置接口停止写入，空间页面移除对应入口。首期保留旧表及历史字段，不为清理旧结构另做破坏性迁移。

## 6. 接口与权限

| 接口或入口 | 开发要求 |
| --- | --- |
| `GET /api/v1/app/skill-ai-review-tasks` | 仅全局审核 Agent 可调用；查询当前有效的待领取尝试，不按空间绑定的 Agent 筛选 |
| `POST /api/v1/app/skill-ai-review-tasks/:requestID/claim` | 保留 `attempt_id`，增加规则版本及摘要；原子领取并返回材料，写入实际执行者 |
| `GET /api/v1/app/skill-ai-review-rule` | 仅指定的活跃审核 Agent 可读取有空间权限的同名已发布规则正文及发布版本；仅明确无已发布规则时返回 `data: null` 以使用随包规则 |
| `POST /api/v1/app/skill-ai-review-tasks/:requestID/result` | 保留尝试 ID、包 SHA-256 与报告/错误互斥契约；校验领取身份及完整报告，再决定后续阶段 |
| `POST /api/v1/app/approvals/skill/:id/ai-review/retry` | 改为当前版本上传者或具备现有相应管理权限的管理员可重试；只限技术异常 |
| `POST /api/v1/app/approvals/skill/:id/ai-review/manual` | 关闭写入口，直接拒绝请求；隐藏 UI 不足以完成改造 |
| 既有个人与管理审批列表、详情 | 返回阶段及可操作能力；“我发起”始终可按权限查看 AI 结果，人工待办只在 AI 通过后出现 |
| 新增 `GET /api/v1/admin/skill-review-workflow` | 返回固定流程定义，ID 为 `builtin:skill-review`，`read_only=true`，触发方式为上传；不返回运行正文 |
| 新增 `GET /api/v1/admin/skill-review-workflow/runs` | 从 Skill 审批记录分页查询本流程执行摘要，可按阶段筛选；详情链接复用现有 Skill/审批详情 |

内置定义沿用现有工作流页面的访问权限。运行列表还须具备既有流程记录查看与 Skill 管理读取权限，并按既有空间访问规则过滤；能看流程定义不等于能看任意 Skill 的报告。分页沿用现有游标风格，默认 20、最大 50，不把分页后的结果冒充完整汇总。

上传者报告访问按认证账号匹配版本的 `uploaded_by_user_id`，并校验当前空间读取权限；审核人沿用本轮名单与空间权限。不能只检查 Skill 最初创建人，也不信任模型或客户端代填的上传者 ID。上传者拥有查看、技术异常重试和重新上传入口，不因此获得审批或评分权限。

`can_process` 只代表人工处理能力。上传者在 AI 阶段的查看和 `can_retry_ai` 必须独立判断，不能因人工不可处理而将报告或重试入口一并隐藏。接口返回标准化错误，避免在异常消息和普通日志中暴露报告正文或凭据。

## 7. 页面与展示

### 7.1 Skill 与上传者入口

- 管理 Skill 列表、个人上传记录的对应版本旁显示阶段和“查看 AI 报告”；详情复用现有报告组件。
- “我发起”可以查看待评估、评估中、需修改和执行异常的记录。需修改时显示具体建议及现有新版本上传入口，技术异常时显示重试。
- 审核人只在 AI 通过后收到可处理待办；评分界面可同时查看完整 AI 报告。报告显示规则版本、执行者、执行时间与覆盖限制。
- 共享客户端若只通过现有企业 Skill 上传入口提交，首期在上传结果中增加当前企业 Gateway 的对应审批详情链接；在 Gateway 登录后查看同一份报告，不另做客户端报告渲染和审批系统。链接只使用已配置企业 origin 和服务端返回的申请 ID，不在 URL 中携带 Token，不新增 Electron Bridge。
- 服务端 Agent 的普通会话列表展示升级后新执行的审核尝试，标题标记“AI 审核 · 只读”，包含 Skill、版本及尝试次数；每次尝试独立成条，旧运行不回填。详情复用本地运行历史并提供 Gateway 审批详情入口，最终结论与流程状态以审批详情为准。会话仅用于查看，不提供继续聊天、编辑消息、恢复执行、取消、改权限、重命名、归档或删除；技术异常重试仍从审批页面发起。展示记录保存在该 Agent 的本地运行数据库，不向 Gateway 普通 Agent 会话活动复制，审核仍使用独立临时工作区和隔离 Runtime，展示会话不绑定或恢复隔离 Runtime 会话。
- 原人工评分维度仍为场景价值、结果有效性、使用便利性、复用价值，每项 1–5 分。全部通过后按维度对审核人取平均再相加，满分 20，AI 结论和建议分不参与统计。

### 7.2 工作流搭建页面

在现有流程模板页面增加固定的“Skill 审批工作流”内置项，与用户配置的通用模板明确区分。可以进入只读详情，查看上传触发、基础校验、AI 评估、人工评分、分值汇总各阶段及其处理规则，审核规则标明由 `skill-review` 维护。

详情提供实际执行记录入口，记录至少包含 Skill、版本、上传者、当前阶段、AI 结论、人工通过人数及正式总分；未产生的内容显示未完成或未评分。每个执行记录使用现有申请 ID，具体规则版本以该次 AI 尝试为准。

内置流程不提供编辑、启停、删除、手工发起或通用实例终止按钮；上传是唯一发起方式。页面状态全部从上述 Skill 记录读取，不向 `workflow_*` 表复制申请、任务和审批决定。通用模板既有功能保持原样。

`server/web` 实施时遵循 `docs/design/design.md` 和 `docs/frontend/frontend-development-guidelines.md`，使用已有组件与路由边界，覆盖加载、空数据、无权限、失败重试和状态变化。

## 8. 一致性、升级与历史数据

1. 上传、申请和待评估尝试同时提交，不能产生“上传成功但永久没有 AI 任务”的半状态。AI 业务未通过的申请可保留内部 `pending`，由派生阶段表示需修改，人工待办查询必须排除它。
2. 领取只能从当前 `pending` 进入 `running`。结果必须匹配申请、尝试、版本摘要和领取者；旧尝试、失效申请、超时后的迟到结果不能推进流程。
3. 网络重传的同一尝试、同一结果应返回已保存结果；内容不同返回冲突。不得因回传失败重复创建申请、人工待办或评分。沿用有界的结果回传重试，不无限重跑模型。
4. 改审核名单、角色成员快照或移动空间时沿用现有重建规则，新轮次也必须重新产生 AI 尝试；旧分数、旧报告保留历史，不作为新轮次放行依据。
5. 已发布版本和已结束历史记录保持可追溯。接入范围内尚未发布且仍可能被发布的旧版本，包括已人工通过但尚未发布的版本，升级时按新规则重建有效审核轮次；旧申请及评分保留历史并标记失效，不能以旧 `manual`、旧无版本报告或无 AI 尝试直接发布。上线前统计并说明受影响数量，不静默抹掉已提交意见。
6. 数据调整通过新增迁移表达，按现有名单快照与角色解析规则处理，不手工修改运行库，不在每次服务启动时重复重建。迁移及行为同步覆盖 `MemoryStore` 和 PostgreSQL 实现。
7. 上线时协调 Gateway、管理台和唯一服务端 Agent，确保新领取接口、审核 Skill 资源、规则版本和报告解析一致。升级窗口任务停留待评估，不借机放行人工；旧 Worker 不能通过新接口缺省字段绕过规则。

## 9. 开发顺序与工作量

整体为中等改动，工作量集中在服务端门禁、待办查询和内置工作流展示。

| 顺序 | 交付内容 | 大小 | 验证 |
| --- | --- | --- | --- |
| 1 | 固定报告契约、阶段规则、可信审核 Skill 和规则版本元数据 | 小到中 | 有效/无效报告、虚构路径、阻断问题与通过结论冲突均有验证 |
| 2 | 新增迁移，全局执行者、领取回传、重试授权、人工及发布门禁 | 中 | 服务层、HTTP 与隔离 PostgreSQL 验证一致，旧记录不能绕过 |
| 3 | Worker 仅服务端启用，显式加载审核 Skill，保留隔离与有界回传 | 小到中 | 正常执行、资源缺失、异常与重启超时；普通客户端不领取 |
| 4 | 上传者报告、修改/重试入口，人工待办与评分联动 | 小到中 | 上传者可看不可评分，AI 未过不出现人工待办，权限变更后重新校验 |
| 5 | 现有工作流页面的内置只读项与实际执行记录 | 中 | 展示与真实审批状态一致，不额外创建通用实例 |
| 6 | 旧未发布数据迁移、全链路回归及受控部署 | 中 | 迁移、完整通过、修改重传、技术重试及既有流程回归 |

客户端上传链接涉及的协议、HTTP client、daemon 路由和共享 Web 只做必要的申请标识透传。实施时先检查当前工作区与已有改动，不重置其他工作，不另建分支或 worktree。

## 10. 验收标准

| 场景 | 必须达到的结果 |
| --- | --- |
| 有效上传 | 同时生成版本、有效申请和待评估尝试；唯一服务端 Agent 能自动领取 |
| 非法包 | 基础校验拒绝，错误明确，不产生成功版本或审核任务 |
| 唯一执行者 | 无空间 Agent 配置；普通客户端或其他 Agent 无法领取、伪造回传 |
| 审核 Skill | 修改检查内容并部署后，新任务使用新版本；运行中任务及历史报告版本不变 |
| 隔离 | 被审材料无法触发脚本、命令、文件读写、MCP 或外部工具；模型调用按现有配置进行 |
| AI 通过 | 只有合法通过报告才开放人工待办；一般非阻断警告可供人工参考 |
| AI 需修改 | 上传者可看完整问题和修改建议；没有人工待办、不能评分或发布，不能转人工 |
| 修改重传 | 新版本重新评估，旧报告和规则版本保留；旧尝试结果不能推进新版本 |
| 执行异常 | 模型超时、规则文件缺失、无效报告等不进入人工；有权限的上传者或管理员可进行有限重试 |
| 授权 | 能看流程定义的人不能越权看报告；非上传者/审核人不能访问他人的未发布版本；撤权后请求失败 |
| 人工与发布 | 部分通过不能发布，任一驳回不能发布；全员通过后正式总分最高 20，仍需手动发布 |
| 所有入口门禁 | 直接接口、管理员、批量发布及旧客户端对接入版本均不能绕过 AI 与人工条件 |
| 并发与重传 | 重复领取只成功一次，同结果回传可重放；新旧尝试、名单变化、空间迁移和迟到结果不串轮次 |
| 工作流页面 | 能查看内置流程和真实上传记录，阶段、报告、评分与 Skill 详情一致；不出现可编辑或手动发起入口 |
| 历史与回归 | 已发布版本可用，旧未发布受控重审；无名单空间、钉钉和 Git 同步未被误纳入或误标已审核 |

## 11. 验证与部署要求

开发验证优先扩展现有 `server/internal/skillhub/ai_review_test.go`、审批/发布及迁移测试，daemon 的 `skill-ai-review-worker.test.ts`、`skill-ai-review.test.ts`，管理台报告、审批、Skill 详情和工作流页面测试。新增用例验证行为和权限，不仅匹配提示词文本。

服务端集成测试使用隔离数据库，由仓库外 `CLAWEE_OPS_DIR` 或 `CLAW_GATEWAY_TEST_DATABASE_URL` 提供配置，禁止连接当前生产库作测试。根目录已有 `pnpm server:test` 包含完整服务端检查；开发中先执行相关用例，再运行所属前端测试与构建。

因会修改 daemon 与可能的共享客户端协议，客户端实现完成后、提交前必须运行根目录 `pnpm desktop:preflight:local`，验证客户端测试、类型检查、实际 App 打包及内嵌 Web 哈希。本文仅为文档变更，不代表这些实现检查已经执行或通过。

部署示例（地址和路径须替换）：服务器 `deploy@192.0.2.10`，服务端 Agent 源码目录 `/home/deploy/work/clawee-agent`，服务为 `clawee-server.service`。服务端 Agent 的源码部署命令在仓库的 `client` 目录执行：

```bash
pnpm server:deploy:source -- --host deploy@192.0.2.10 --dir /home/deploy/work/clawee-agent
```

示例私有 `server.toml` 位于服务器 `/home/deploy/data/server.toml`，在其中的 `[server]` 段设置上述开关。对应 systemd 服务在源码目录执行以下命令加载该文件：

```bash
/usr/bin/pnpm server:start -- --server-config=/home/deploy/data/server.toml
```

只修改配置文件时，在服务器执行 `sudo systemctl restart clawee-server.service` 后生效，无需重新构建。该路径由 `--server-config` 指定，不是相对于源码目录自动查找；打包部署则沿用 `config/server.toml`。

该部署命令仅部署并重启服务端 Agent，不代替 Gateway、管理台和数据库迁移部署，也不会同步 Gateway 的 YAML 配置。Gateway 的 `skillhub.review_agent_id` 修改后须单独同步配置并重启 Gateway，应使用 Agent 已登录企业会话返回的稳定 ID；该 ID 可能与本地安装 ID 不同。本地兜底规则必须随源码同步；优先使用的 Hub 规则须已发布，并为审核账号授予该规则空间的读取权限。登录身份、稳定 Agent ID、模型凭据和运行数据保存在源码目录外，部署后不能生成另一个 Agent 身份。Gateway 的唯一执行者配置与 daemon 的 Worker 开关也应保存在既有运维配置中。

上线前检查：唯一 Agent 身份与目标空间权限、模型可用性、可信审核 Skill 文件、迁移影响数量、全链路本地结果。部署后使用专用验收 Skill 完成通过、需修改、执行异常三条链路，核对上传者视图、人工待办和工作流页面；不得重启其他服务或用现有用户材料试错。
