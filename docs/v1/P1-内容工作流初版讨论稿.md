# 内容工作流初版讨论稿

> 状态：讨论中  
> 用途：用于客户调研和方案讨论，不代表最终设计或当前已实现能力。

## 讨论目标

探索在 Codex 上实现以下内容工作流的可行方案：

```text
热点发现 -> 选题判断 -> 脚本生成 -> 人工审核 -> 发布任务 -> 数据回流
```

当前阶段只确定总体方向和关键边界。具体节点、状态、接口和数据结构，需要结合客户实际工作方式再决定。

## 当前方向

在 MCP Gateway 后台提供一个轻量 Workflow Service，用于管理工作流状态、执行节点和串行推进。

```text
Workflow Service
    -> Codex Runner
    -> 人工审核
    -> 发布连接器
    -> 热点、素材和数据等企业能力
```

主要职责暂定如下：

- Workflow Service：保存状态，按顺序推进节点，处理等待、超时、重试和恢复。
- Codex Runner：完成热点整理、选题判断、脚本生成和数据复盘等智能任务。
- 人工审核：暂停流程，等待人工批准或驳回。
- 发布连接器：执行实际发布，并避免重复发布。
- MCP Gateway：提供身份、权限、门禁和审计能力，管理企业系统接入。

Gateway 初版只承载必要的流程管理和系统接入能力，不建设完整的内容平台、素材平台或数据分析平台。

## 初版执行模型

一个工作流包含多个执行节点，节点按照固定顺序串行执行。

初步考虑三类节点：

- `codex`：调用 Codex 完成判断或内容生成。
- `approval`：等待人工审核结果。
- `publish`：调用发布连接器完成发布。

示例：

```text
热点发现 Codex
-> 选题判断 Codex
-> 脚本生成 Codex
-> 人工审核 Approval
-> 发布 Publish
-> 数据回流 Codex
```

Workflow Service 是流程状态的唯一来源。节点只报告执行结果，不能自行跳过节点或修改整体流程状态。

## 初版运行要求

- 节点严格串行执行，暂不支持分支、并行和循环。
- 每个节点保存输入、输出和执行状态，后续节点读取前序结果。
- Codex 每个节点独立执行，不依赖长期保持的聊天上下文。
- 审核节点进入等待状态，收到审核结果后继续或结束。
- Codex 不直接执行发布，发布由独立节点完成。
- 发布需要校验审核结果，并具备最基本的幂等控制。
- 执行失败后可以有限重试；服务重启后可以从未完成节点恢复。
- 数据回流可以在发布后延迟到指定时间继续执行。

## 初版状态

工作流和节点暂时共用一组简单状态：

```text
pending
running
waiting
succeeded
failed
rejected
timed_out
```

具体业务阶段由当前节点表示，不为每个内容阶段单独设计状态。

## 初版暂不考虑

- 可视化流程编辑器。
- 复杂分支、并行、循环和子工作流。
- 节点动态插入或自动修改流程。
- 多级会签和复杂审批策略。
- 通用表达式语言。
- 完整的素材管理、内容管理和数据分析能力。
- 驳回后的自动返工循环。

## 客户调研重点

后续需要通过客户访谈确认：

1. 实际工作流包含哪些阶段，顺序是否固定，哪些阶段可以跳过或退回。
2. 选题和脚本分别是否需要审核，由谁审核，审核意见如何处理。
3. 热点、素材、发布和数据目前分别来自哪些系统，是否具备 API 或 MCP 接入条件。
4. 发布是要求全自动执行，还是只生成发布任务并由人工完成。
5. 发布失败、审核超时和人员未处理时，客户当前如何处置。
6. 数据需要在什么时间回流，关注哪些指标，回流结果用于什么决策。
7. 单日任务量、并发量、平台数量和账号数量大致是多少。
8. 哪些操作必须保留人工确认、权限控制和审计记录。

## 当前待讨论问题

- Workflow Service 是否作为 Gateway 内部模块提供，还是后续拆成独立服务。
- 初版是否只保留脚本审核，暂不设置选题审核。
- 发布节点是直接发布，还是先创建发布任务交给人工处理。
- 数据回流是否属于同一次工作流运行，还是单独创建后续任务。
- 客户是否需要在管理控制台中查看和操作工作流。

以上问题暂不做结论，待客户调研后继续调整。
