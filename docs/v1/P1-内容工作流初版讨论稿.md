# 工作流初版方案设计

> 状态：方向已确认，本文为初版开发契约；尚未实现。
> 范围：通用工作流编排、审批、客户端 Agent 任务和实例查看。内容工作流只是后续配置案例。

## 1. 目标与范围

在 Gateway 管理控制台的“工作台”可视化配置串行工作流模板；模板第一个节点的负责人在客户端 APP 发起实例。Gateway 保存模板、实例、节点任务与审计，客户端主动拉取本人任务并提交结果；Gateway 收到节点输出后推进到下一节点。参与者在客户端查看进度及全部已产生的节点输入、输出，管理员在控制台查看并可终止实例。

初版仅有`approval`（审批）和`agent`（Agent 执行）两类节点，按固定顺序逐个执行。不做分支、并行、循环、子流程、动态改图、自动返工、定时调度、自动发布连接器或数据回流。下面这条链路只说明后续案例，不是初版验收场景：

```text
热点发现 -> 选题判断 -> 脚本生成 -> 人工审核 -> 发布任务 -> 数据回流
```

案例中的发布任务确定由人工处理；如何映射到两类基础节点留待配置该案例时解决，不因此扩充初版模型。数据回流目前只是诉求点，暂不设计。

## 2. 系统边界

- `server` 的 Workflow Service 作为 Gateway 内部模块，以 PostgreSQL 为状态唯一来源。服务负责校验模板、创建实例与任务、推进状态、权限和审计；不在服务端运行 Codex。
- `server/web` 管理控制台新增“工作台”：模板列表、可视化编辑器、实例列表和详情。仅管理员能编辑模板、启停模板、查看所有实例及终止实例。
- `client/apps/web` 共享界面新增工作流模板、实例与待办入口；桌面和浏览器使用同一份页面。界面沿现有客户端企业会话路径，经 `client/apps/daemon` 的企业接口访问 Gateway `/api/v1/app`，不在 Web 层保存 Gateway 凭据或执行 Agent 任务。
- 客户端 Agent 通过 Gateway `/mcp` 的内建工作流工具取任务与提交输出；它不是 daemon 本地 `/mcp` 的任务工具。daemon/本地 Codex Runtime 负责实际执行及本地失败处理，模型配置、运行记录和凭据仍留在本机。纯浏览器入口没有本地 Runtime 时可查看模板、实例与处理人工审批，但不展示不可执行的 Agent 操作。
- Gateway 不轮询客户端、不代执行、不因客户端离线自动跳过节点。提交节点结果之前，实例停在当前节点。

开发落点：新增 `server/internal/workflow` 服务与存储、对应数据库迁移；在 `server/internal/server/http.go` 的 app/admin 路由挂载业务接口，并在 `server/internal/mcpserver/server.go` 为 Gateway 根 MCP 注册内建工具。客户端沿既有 daemon 企业 HTTP client 和 `client/apps/web` service/route 接入；控制台沿 `server/web` 现有 API、路由与权限导航接入。以上均为新增能力，不能视为当前已有接口。

## 3. 模板与编排

模板字段：`id`、名称、描述、`status`、`revision`、按 `order` 升序排列的节点、创建/修改人和时间。状态为 `draft`、`enabled`、`disabled`；仅 `enabled` 可由首节点负责人发起。草稿允许逐步保存，启用时必须完整校验；停用只禁止新实例，不影响已启动实例。修改已启用模板时校验完整配置并增加 `revision`，已启动实例仍执行自己的快照。

节点字段：稳定的 `node_id`、`order`、`type`、标题、`assignee_user_id`、说明/任务指令。`approval` 节点展示输入，负责人作出批准/驳回决定并可填写意见；初版不在审批页改写输入，批准后的节点输出等于输入，决定与意见另行记录。`agent` 节点给本地 Agent 提供指令和输入，由 Agent 提交 JSON 对象输出。节点负责人在模板中固定指定为一个有效账号；一个用户可负责多个节点。模板所有节点负责人及发起人构成实例参与者。

工作台的可视化编辑器采用按执行顺序排列、连线的节点视图，支持添加、删除、上移/下移节点、编辑标题/指令/负责人、保存草稿、启用/停用及查看校验错误；键盘操作也能调整顺序。初版无自由连线或图布局坐标，存储的顺序即执行顺序，避免画布与执行定义分叉。启用和已启用模板的保存必须校验：至少一个节点、`order` 唯一且连续、`node_id` 唯一、类型合法、指令非空、负责人存在且有效；不提供条件表达式或上下文映射器。

发起实例时首节点负责人可提交可选的初始输入 JSON 对象，默认为 `{}`。节点任务的 `input` 始终等于发起输入或上一个已完成节点的 `output`，节点指令另行展示，不悄悄拼接或改写输入。节点输出限制为 JSON 对象，供下一节点原样读取；审批批准时输出自动保留原输入，驳回时记录决定并结束实例，不生成下一个任务。附件如有需要，由已有共享文件能力提供引用，不把文件二进制放入节点输出。

## 4. 实例、任务和状态

| 对象 | 状态 | 触发与结果 |
| --- | --- | --- |
| 模板 | `draft` / `enabled` / `disabled` | 管理员保存、启用或停用；编辑导致 `revision` 增加 |
| 实例 | `running` / `succeeded` / `rejected` / `terminated` | 发起后运行；最后节点完成、审批驳回或管理员终止后进入终态 |
| 节点任务 | `pending` / `completed` / `rejected` / `cancelled` | 进入节点时待处理；提交成功/驳回；实例终止时取消当前待办 |

服务端不设“已领取”或“执行中”状态：领取只是查询当前任务输入，不加锁、不转移负责人、不触发流转；本地执行进度属于本地运行。客户端离线或本地 Agent 失败时，任务保持 `pending`，Agent 自行处理失败，未提交有效输出不会推进流程。

一个实例只有一个当前节点和至多一个 `pending` 任务。发起时写入模板 `id`、`revision`、完整节点定义快照、参与者快照、初始输入和首节点任务。完成提交在同一数据库事务中锁定实例，验证 `running`、当前任务 `pending` 和提交者为当前负责人，再保存输出、关闭当前任务；若有下一节点，则用完整输出作为下一任务输入并更新当前节点，否则结束实例。审批驳回记录意见并结束，管理员终止实例同时取消当前任务。停用模板、修改模板或 Gateway 重启不会改变运行中实例。

两次并发提交/终止按数据库事务串行化：先完成者生效，后到者收到状态冲突。发起实例和完成任务分别携带 `idempotency_key`；同一账号在同一模板下的发起请求、同一任务的完成请求，若以相同 key 和内容重试，返回首次保存的结果，不重复创建；相同 key 不同内容或用新 key 重提已完成任务均返回 409。终止不能撤回本地 Agent 已产生的外部副作用；终止后未完成任务的提交返回冲突，已完成任务的同 key 重试只重放旧结果，不再流转。

## 5. 持久化契约

通过 `server/db/migrations` 新增表，迁移号以实施时的下一个可用编号为准：

| 表 | 核心字段与约束 |
| --- | --- |
| `workflow_templates` | `id`、`name`、`description`、`status`、`revision`、`definition_json`、`created_by`、`updated_by`、时间；定义保存有序节点数组 |
| `workflow_instances` | `id`、`template_id`、`template_revision`、`template_snapshot_json`、`status`、`current_node_id`、`initial_input_json`、`started_by`、发起幂等 key/请求摘要/首次响应、开始/结束时间；`(template_id, started_by, 发起幂等 key)` 唯一，运行只读快照 |
| `workflow_instance_participants` | `instance_id`、`user_id` 唯一；用于参与者列表和详情授权，实例创建时按快照写入 |
| `workflow_node_tasks` | `id`、`instance_id`、`node_id`、`node_order`、`type`、`assignee_user_id`、`input_json`、`output_json`、`status`、审批决定与意见、完成幂等 key/请求摘要/首次响应、处理人与时间；`(instance_id, node_id)` 唯一 |
| `workflow_events` | `id`、可空的 `template_id`/`instance_id`/`task_id`、`event_type`、`actor_user_id`、`actor_agent_id`、`created_at`、必要元数据；只追加，不复制输入输出正文 |

为实例的 `status`/创建时间、参与者的 `user_id`、待办的 `assignee_user_id`/`status` 建索引。JSON 字段只存可序列化输入/输出，不存模型密钥、Gateway Token 或客户端本地运行上下文。业务数据大小上限初版按单次输入/输出各 1 MiB 校验，超限拒绝；审计和普通访问日志不记录任务正文。列表按稳定时间与 ID 排序并分页。

## 6. HTTP 与 MCP 契约

沿用 Gateway `/api/v1` 的 `{data, meta}` 成功响应及现有错误格式，列表使用 `limit`（默认 20，最大 50）和不透明 `cursor`。以下为新增路由，不改动本地 daemon 的已有任务 API。

| 接口 | 用途与权限 |
| --- | --- |
| `GET/POST /api/v1/admin/workflow-templates`、`GET/PUT /api/v1/admin/workflow-templates/:id` | 管理员列表、详情、创建及保存；修改请求带 `expected_revision`，冲突返回 409 |
| `POST /api/v1/admin/workflow-templates/:id/enable`、`POST /api/v1/admin/workflow-templates/:id/disable` | 管理员校验后启用或停用模板 |
| `GET /api/v1/admin/workflow-instances`、`GET /api/v1/admin/workflow-instances/:id`、`POST /api/v1/admin/workflow-instances/:id/terminate` | 管理员查看全部实例并终止运行中的实例；终止请求记录原因与操作者 |
| `GET /api/v1/app/workflow-templates`、`GET /api/v1/app/workflow-templates/:id` | 当前账号可见的已启用模板；参与人可查看节点配置 |
| `POST /api/v1/app/workflow-templates/:id/instances` | 仅模板首节点负责人发起；请求含 `initial_input` 与 `idempotency_key`，返回实例与首任务 |
| `GET /api/v1/app/workflow-instances`、`GET /api/v1/app/workflow-instances/:id` | 仅实例参与者；默认运行中，`status` 可筛历史；详情返回所有节点的已有输入、输出和审批结果 |
| `GET /api/v1/app/workflow-tasks`、`GET /api/v1/app/workflow-tasks/:id` | 当前账号的待办与任务详情；他人任务不可处理 |
| `POST /api/v1/app/workflow-tasks/:id/decision` | 仅当前审批负责人；`decision=approve/reject`、`comment`、`idempotency_key`；服务端生成审批输出并推进或驳回 |

APP 接口使用现有 frontend audience 与账号/Agent 绑定验证；控制台接口使用 admin audience 和新增的工作流模板管理、实例查看、实例终止 RBAC 权限，并同步更新 RBAC 目录和默认管理员角色。不因拥有控制台权限而允许代替负责人审批或执行 Agent 任务。已启用模板只对其固定节点负责人可见；实例的参与者为创建时快照中的全部负责人。服务端对每次列表、详情及操作独立授权，客户端过滤和隐藏按钮只改善交互，不作为权限依据。

模板保存请求用完整有序节点数组替换当前定义，服务器按 `expected_revision` 做乐观并发校验；发起和审批提交的最小请求如下：

```json
{
  "name": "示例流程",
  "description": "",
  "expected_revision": 1,
  "nodes": [
    { "node_id": "node_1", "order": 0, "type": "agent", "title": "整理", "assignee_user_id": "user_1", "instruction": "整理输入内容" },
    { "node_id": "node_2", "order": 1, "type": "approval", "title": "审核", "assignee_user_id": "user_2", "instruction": "确认结果" }
  ]
}
```

`POST /api/v1/app/workflow-templates/:id/instances` 使用 `{ "initial_input": { "text": "原始内容" }, "idempotency_key": "start-unique-key" }`；`POST /api/v1/app/workflow-tasks/:id/decision` 使用 `{ "decision": "approve", "comment": "通过", "idempotency_key": "decision-unique-key" }`。这两类响应均返回稳定的实例 ID、任务 ID 与本次流转结果，不依赖客户端猜测下一节点。

Gateway 根 `/mcp` 注册三项内建工具，使用现有账号 MCP Token、`X-Claw-Agent-ID` 与绑定校验，从认证身份取得 `user_id`/`agent_id`，工具参数不接受代填用户 ID：

| MCP 工具 | 输入 | 输出/作用 |
| --- | --- | --- |
| `workflow_list_tasks` | 可选 `cursor`、`limit` | 仅该账号负责且仍为当前节点的 `agent` 待办摘要；不执行任务 |
| `workflow_get_task` | `task_id` | 仅本人当前 `pending` Agent 任务的指令与完整 `input`；这是“领取”，无状态变化 |
| `workflow_complete_task` | `task_id`、`output` JSON 对象、`idempotency_key` | 提交当前节点输出并请求流转；返回实例状态和下一节点摘要，不返回非本人下个任务的私有操作入口 |

MCP 工具在 `server/internal/mcpserver` 直接注册，调用同一个 Workflow Service，不通过对外上游 MCP 代理绕行；工具本身可见不代表可访问任意任务，每次调用仍校验 Agent 活跃、账号归属、负责人及任务状态。读取任务不触发 Agent 运行；工具错误返回稳定业务错误码，不泄露他人输入。管理台与 APP 的 HTTP 写操作和 MCP 完成操作走同一事务/状态机，不允许两套独立流转逻辑。

任务详情示例（HTTP 返回 `data` 包装，MCP `structuredContent` 为同一任务对象）：

```json
{
  "task_id": "task_123",
  "instance_id": "instance_123",
  "node_id": "node_1",
  "type": "agent",
  "status": "pending",
  "instruction": "整理输入信息并输出结果",
  "input": { "text": "待处理内容" }
}
```

Agent 完成工具的请求示例：

```json
{
  "task_id": "task_123",
  "output": { "text": "已完成的工作内容" },
  "idempotency_key": "client-generated-unique-key"
}
```

正常状态冲突返回 HTTP 409；未认证 401、能查看但无权操作 403、不存在或不可见 404、无效字段 400、输入/输出超限 413、依赖不可用 503。MCP 返回对应稳定 `code`，客户端不得将超时/断线当作提交失败而生成新 key；先以相同 key 重试或刷新任务状态。模板及任务正文不得进入错误消息和日志。

## 7. 界面与客户端执行

工作台：模板列表显示名称、启用状态、版本和首节点负责人；编辑器左侧按顺序绘制节点与连线，选中后配置两类节点的共用字段；保存与启用分开，错误定位到节点。实例列表支持状态筛选，详情沿同一流程视图标记当前/已完成节点、输入输出、处理人和时间；运行中提供有权限的“终止”操作并确认原因。与 `server/web` 既有组件、导航和权限门禁保持一致。

客户端 APP：模板列表可进入详情；首节点负责人可发起并输入初始内容。实例列表默认显示本人参与的运行中实例，支持历史筛选；实例详情显示所有节点配置与已有输入输出，未执行节点只显示静态定义、不伪造输出；当前本人待办提供审批或 Agent 执行入口。审批页可见原输入，批准/驳回及意见提交后刷新详情。daemon 工作流适配层以当前账号的 Agent 身份调用 Gateway MCP，执行入口建立本地任务并记录 Gateway `task_id` 与本地 run 的关联；本地 run 成功后把最终文本构造为 `{ "text": "..." }` 输出，用稳定的幂等 key 调用完成工具。该 key 与任务/run 关联在本地持久保存直至服务端确认，断线重试不能重新生成。打开详情或查询待办本身不启动执行，失败由本地 Agent 流程处理并允许后续使用同一待办重新执行，Gateway 保持 `pending`。若本地执行能力不可用，不显示无效的执行按钮。

客户端可在登录且在线时刷新待办，不依赖服务端主动推送；离线只展示已取得的本地缓存（若已有），不得把缓存当成可提交的最新状态。恢复连接后重新查询任务；被终止或已经完成的任务在 UI 上停止提交并提示状态变化。普通参与者对同一实例的全部已产生节点输入、输出默认可见，非参与者不可见。

## 8. 实施顺序与验收

1. Gateway：建表与 Workflow Service、状态事务、权限和审计；用服务层及隔离数据库测试验证模板快照、顺序流转、审批驳回、终止与提交竞态、幂等和参与者可见性。
2. 接口：接入 app/admin HTTP 与 Gateway 根 MCP 工具；测试账号/Agent 绑定、他人任务拒绝、输入输出大小、分页、重复提交及 Gateway 重启后的待办恢复。
3. 管理台：模板列表/可视化编辑器、启停和实例详情/终止；测试顺序调整与保存结果一致、无权限隐藏及服务端 403。
4. 客户端：通过 daemon 企业接口接入共享 Web 的模板、实例和审批界面；本地 Agent 任务与 Gateway MCP 结果提交打通；测试桌面/浏览器能力差异、离线不推进和本地失败后仍可处理。

端到端验收用最小 `agent -> approval -> agent` 模板：首节点负责人发起，第一节点读取初始输入并提交输出，审批负责人查看该输出并批准，末节点收到完全相同的审批输出；实例成功结束。另验驳回不生成末节点任务、管理员终止后提交冲突、参与者能看全部已有输入输出但非参与者不能读取、重复完成只流转一次、客户端离线不执行。测试数据使用隔离环境，不触碰现有用户或生产实例。

开发客户端可执行代码后，按仓库要求运行 `desktop:preflight:local`；本文仍是方案，不代表接口或页面已经交付。
