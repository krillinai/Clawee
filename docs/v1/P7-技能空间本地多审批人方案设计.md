# 技能空间本地多审批人方案设计

> 状态：开发落地方案。范围：Gateway Skill Hub 与 `server/web` 技能管理界面；仅改本地审批，不改钉钉 OA、客户端本地 Skill 审批或其他业务的审批流程。

## 1. 目标和边界

一个技能空间可以配置多名本地审批人。版本由该次申请的全部审批人通过后，才允许按现有方式手动发布；任一人驳回则不能发布。未配置审批人的空间仍由上传者自行发布。已有钉钉 OA 空间保持原规则，包括 Git 同步版本的现有发布方式。

本次只让**存储结构**能承载其他业务的审批，不建设通用审批平台、流程编排、审批比例、角色审批、通知或自动发布。服务端技能业务仍负责其权限、版本状态和发布门禁；`client/apps/daemon` 的 Runtime 审批、MCP 门禁与 `workflow_*` 表不纳入改造。

现状是 `skill_spaces.approver_user_id` 只能存一人，`ReviewVersion` 一人通过就将 `skill_versions.approval_status` 设为 `approved`，`setCurrentVersion` 据此放行。改造必须同时覆盖配置、审批记录、服务端发布门禁和前端入口，不能只换多选控件。

## 2. 最小数据结构

新增顺序迁移，不改写既有迁移。保留 `skill_versions.approval_status` 作为技能页面和发布查询使用的汇总状态；多人的权威记录放在以下三张表。

| 表 | 核心字段与约束 | 本次取值 |
| --- | --- | --- |
| `approval_config_approvers` | `scope_type`、`scope_id`、`user_id`，三列联合唯一 | `skill_space`、空间 ID、审批人账号 ID；没有行表示未开启本地审批 |
| `approval_requests` | `id`、`business_type`、`business_id`、`action`、`scope_type`、`scope_id`、`content_digest`、`status`、创建/结束时间 | `skill_version`、版本 ID、`publish`、`skill_space`、空间 ID、包 SHA-256；状态为 `pending/approved/rejected/invalidated` |
| `approval_request_approvers` | `request_id`、`user_id`、`status`、`comment`、`decided_at`，`(request_id,user_id)` 唯一 | 每次申请创建时复制审批人名单；个人状态为 `pending/approved/rejected` |

申请和个人决定通过外键关联；按业务类型、业务 ID 和动作建立查询索引，同一业务对象同一动作最多一条 `pending` 申请。`business_id` 是业务引用，不伪造跨业务外键；申请创建及发布时由 Skill Hub 校验版本、空间和包摘要。审批人必须是有效账号并具备现有技能查看权限。无需额外的审批策略表、配置版本、通用 JSON 字段或通用业务回调。

每次申请的人员表是**快照**，不按审批时的空间现有名单动态计算。技能版本上的 `reviewed_by`、`reviewed_at`、`review_comment` 不再作为本地多审批的判断依据；详情改为读取申请和个人记录。已发布旧版本的历史单人摘要不强制改写。

## 3. 状态与一致性

1. 上传新版本时，若所属空间是本地审批且配置了审批人，则创建 `pending` 申请和全部 `pending` 个人记录；无审批人时不创建申请，沿用现有自发布路径。仅支持**全员会签**，不提供其他规则选项。
2. 本人只能决定自己在当前有效申请中的一条 `pending` 记录。服务端仍检查账号有效、空间为本地审批、版本所属空间及技能查看权限；重复决定或已结束的申请返回冲突。决定及汇总在同一事务内完成：一人驳回 -> 申请和版本 `rejected`；全部通过 -> 申请和版本 `approved`，记录当前 `approved_space_id`；否则均保持 `pending`。驳回后不能直接改判，修订内容需上传新版本。
3. 发布仍由现有发布操作触发，不因最后一人通过自动发布。所有本地发布入口，包括管理员发布、批量发布和上传者自行发布，必须在发布事务内核验：有审批人时，有匹配当前版本、空间、包摘要的有效 `approved` 申请及 `approved` 版本；无审批人时只允许沿用原有上传者自发布条件。钉钉空间继续走现有 OA 门禁，不能落入本地或自发布分支。
4. 修改本地审批人名单（包括关闭审批）时，在一个事务内更新名单，将该空间**未发布版本**的旧申请标为 `invalidated`，清除旧版本审批结论，并按新名单重建待审申请；名单为空则回到无审批状态。已发布的当前版本、`current_version_id` 和可用性不变。技能移入其他空间时沿用现有撤销发布/重置审批规则，旧申请失效，按目标空间名单重新开始。旧申请保留用于核查，但不参与发布判断。
5. 配置保存与审批提交都按空间/技能的固定加锁顺序串行化；两人同时通过不能丢失结果，名单变更后迟到的旧审批不能重新批准版本。钉钉审批方式与本地名单的切换必须原子完成，不能出现先切到“本地且无审批人”、再单独写入名单的自发布窗口。

## 4. 接口与界面

- 空间配置读接口返回 `approvers: [{ user_id, name }]`；现有候选人接口继续提供可选账号。写入采用完整 `approver_user_ids` 数组，一次替换名单，服务端拒绝重复、无效或无技能查看权限的账号。切换到本地模式时，审批方式与名单在同一事务提交；钉钉配置接口其余行为不变。
- 当改名单会重置未发布版本的审批时，第一次保存返回“需要确认”及受影响版本数，不改动数据；界面确认后携带确认标记重试，由服务端在事务中重新核对影响范围并完成更新。没有受影响版本时直接保存。配置更改仍沿用空间更新权限和操作日志。
- 版本详情返回本地审批的总人数、已通过人数，以及每位审批人的姓名、状态、时间和意见；仅当前申请用于进度与按钮状态。未配置审批人或使用钉钉 OA 时不展示本地审批人员列表。审核接口保留原路由和决定/意见字段，返回更新后的版本与审批进度。
- `server/web/src/components/skill-spaces-panel.tsx` 的“开启审批”开关和“空间设置”抽屉不变：本地审批人单选改为可多选列表，显示已选姓名并可移除；人数多时支持列表内搜索。开启审批时至少选一人，字段旁显示“需全部通过”；空间列表显示名单或人数。名单变更需要重审时才弹确认框。
- `server/web/src/pages/skills.tsx` 和 `pages/skill-detail.tsx` 显示“已通过 X/Y”及逐人状态；只给本人且仍待审的记录展示通过/驳回操作。未全员通过前发布按钮不可用，但按钮状态不替代服务端校验。`pages/app-skills.tsx` 的无审批自发布入口继续仅在名单为空时出现。原有按 `approverUserId` 判断能否审核、发布的代码全部改用多人名单/个人状态。

## 5. 迁移、落点与验收

- 迁移现有 `approver_user_id` 到配置表，保持原有单人空间生效；为**未发布**且已有审批人的版本建立申请快照，保留可验证的原审批结论，无法匹配当前空间/审批人的旧批准不得自动放行。已发布版本不撤下。完成代码和数据迁移后，移除对单人字段的读写；回滚及迁移测试须覆盖这一顺序。
- 后端落点：`server/db/migrations`、`server/internal/skillhub/approval.go`、`approval_postgres.go`、`postgres_store.go`、`spaces_postgres.go`、`external_approval_postgres.go`（仅处理与本地切换的边界）、`server/internal/server/skill_spaces_http.go` 与 `skillhub_http.go`；同步维护 `MemoryStore`。前端落点：`server/web/src/lib/skillhub-api.ts`、空间设置、技能列表与详情及相邻测试。
- 验收覆盖：旧单人配置迁移；零人自发布、一人审批、多人的部分通过/全员通过/任一驳回；未授权、停用账号、重复和并发审批；改名单确认与旧申请失效；技能迁移；管理员、批量和自发布入口均不能越过门禁；钉钉空间及其 Git 同步规则不变。后端集成测试只使用隔离测试数据库。
