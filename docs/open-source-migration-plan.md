审查及决策更新日期：2026-09-08。状态：源码整合与本机验收已完成，当前交付 `clawee` 分支的独立源码快照。优先公开自有代码，保留已验证的依赖与锁文件；第三方再分发许可补齐或替换留作后续专项，不再阻塞源码整理、提交与公开。正式安装包、镜像及签名公证另行验收。

最新执行顺序：源码已推送，当前优先按[功能验证与操作指南](validation-and-operations.md)在整合仓库确认启动、功能和部署，尽量沿用原组件命令。普通 CI 验证、默认分支切换和分支保护均后置，与签名、许可专项及发行操作统一记录在[正式发布前待处理事项](pre-release-checklist.md)。下文保留整合阶段方案与既有验证记录，不表示本次逐项功能验收或正式发行已完成。

## 1. 确定方案

将两个项目作为同一个 Clawee 项目的客户端和服务端，在当前仓库、当前 `clawee` 分支内整合为 monorepo。第一阶段保留两个组件的目录结构和构建体系，以经过筛选、脱敏的源码快照开始新的公开历史。

首发目标是：外部用户无需访问原私有仓库、现有运营网关或独立模型管理服务，即可部署服务端，连接桌面客户端，使用自己配置的模型服务完成一次任务和一次受权限控制的 MCP 调用。

开源范围已确定为两仓库中拥有发布权的全部通用功能。计费、钉钉、百炼等外部集成保留为可选能力；客户资料、真实运维配置和内部工作流不进入公开仓库。本轮不另设闭源企业版，也不新增双许可机制。

| --- | --- |

| 桌面更新 | `krillinai/Clawee` 的 GitHub Releases，正式版使用 stable 渠道 |

| 后续专项 | 第三方许可补齐或依赖替换、正式产物再分发审查；macOS 签名与公证由有权限的同事后置处理 |

## 3. 公开前的阻断项

### 3.1 凭据、历史配置和调试产物

已确认：

- 客户端有 **193 个 `.tmp/` 文件已被 Git 跟踪**，包括截图、Playwright trace、JSON/JSONL 和 trace 资源；其中含开发机绝对路径。是否还含真实会话或凭据，需进一步检查，不能作为普通源码整体公开。
- 服务端最新提交 `08a1d7d` 已将真实配置改为 `configs/config.example.yaml`。旧提交 `112c2db` 的 `configs/config.yaml` 仍有多个非空敏感字段，包括管理 Token、JWT 签名密钥、Agent Token 加密密钥和外部集成凭据。这里只记录字段类型，不复制具体值；未验证凭据是否真实、有效或已轮换。
- 服务端 `.mcp.json` 虽已写入忽略规则，仍在 Git 跟踪清单内。说明仅追加 `.gitignore` 不能处理已经跟踪的文件。
- 客户端跟踪了内部 Bug 处理技能；服务端跟踪了开发技能、Hook 和内部流程材料。这些都需要独立筛选。

处理方案：

1. 按源码白名单选择导入文件，再叠加禁止导入清单。源仓库不做批量删除或历史重写。
2. 不导入 `.git`、`.env`、真实配置、数据库、用户附件、`.runtime`、`.tmp`、构建缓存、现有 release 包、测试报告和截图。测试所需的虚构 fixture 单独审核后保留。
3. 内部技能、Hook、MCP 配置、客户部署材料和历史计划报告默认排除；正式开发文档和必要架构决策单独整理。不要启用或调用 Superpowers。
4. 对源仓库全部可访问分支/Tag 历史执行凭据扫描，用于识别需轮换的旧凭据；对候选导入目录和最终公开 Git 历史分别扫描。使用支持脱敏输出的 Gitleaks 等工具，报告保存在公开目录之外。
5. 输出需吊销或轮换的真实凭据清单，具体值不进入公开材料。新部署生成全新密钥；旧私有部署的凭据处置单独进行，不为开源版本实现旧密文兼容，也不直接替换旧实例的加密密钥或删除其数据。
6. 对图片、压缩包、trace、数据库和 Git LFS 对象单独检查，文本扫描不能替代这些检查。检查首次发布附件、日志和镜像层，确保没有重新带入敏感文件。

已确定新历史导入，因此旧私有提交、Tag 和分支不推送到新仓库，不使用 mirror push，不执行旧仓库历史重写。

### 3.2 默认配置仍依赖现有运营环境

具体证据：

- `clawee-agent/config/config.toml:1` 默认指向现有运营网关；`scripts/server-package.mjs:410` 的示例生成也写入该网关。
- `apps/daemon/src/enterprise/development-config-2026-08-09.ts:26` 会用模板网关覆盖已有开发配置的 gateway，仅保留 agentId。仅修改运行时配置可能在下一次启动时被覆盖。
- `claw-mcp/configs/config.example.yaml:69` 仍配置 `platform_managed`；`internal/config/config.go:453` 的默认值相同。
- `internal/server/model_configuration_http.go:48` 已支持 `enterprise_managed` 直接返回模式；平台托管分支需要 ModelConfigurationProvider，失败时返回 503。
- `clawee-agent/apps/daemon/src/codex/model-service-configuration.ts:219` 已有 `enterprise_managed` 下读取或要求用户填写模型配置的流程。

处理方案：

- 开源自托管示例默认使用现有的 `enterprise_managed` 模式，复用客户端模型配置流程；不新增第三套模式。
- 开发示例连接本地 Gateway；分发的桌面 App 首次使用时允许设置服务端地址，不能默认把社区用户送入现有运营服务。
- 明确配置优先级，使用户选择的网关在重启和升级后保持稳定；更换网关时清除或按网关隔离认证状态，防止旧 Token 发往新地址。
- 保留平台托管模型、计费、钉钉、百炼等适配器，但只有显式配置后才启用。前端根据服务端能力状态处理入口与错误，不能未配置就卡住登录、启动或基本任务。
- 实际验证初始化、注册、登录、Agent 绑定、模型配置等全链路。模型配置已有分支不等于所有外部依赖都已解除。

### 3.3 开源许可与第三方再分发

项目许可证已确定为 **Apache-2.0**，不再进行 MIT/AGPL 选型。LICENSE 使用标准许可原文，中文说明放入 README 或贡献文档。

导入时核查员工、外包、合作方和复制代码的已有归属声明。许可证不能覆盖没有再授权权利的第三方材料；第三方依赖与资产核查属于执行检查，不重新打开项目许可证决策。

依赖清单至少覆盖 npm、Go、Electron、嵌入的 Codex Runtime、其内含可执行文件、字体、图标、图片和内置 Skill。客户端 Runtime 清单明确包含 rg、zsh、bwrap 等不同平台资源，不能仅检查顶层包的许可。逐项核对实际发布版本的 LICENSE/NOTICE、修改情况和源码提供义务，并确保需要的文本进入源码包、桌面安装包和镜像。

产出根目录 LICENSE、必要的 NOTICE、第三方许可清单及 SBOM。包中的 `private: true` 可以保留，它限制 npm 发布，不影响 GitHub 开源。补齐 package metadata 中适用的 license、repository 和 homepage。

### 3.4 自托管安全边界

这部分列为待验收条件，不代表已经发现对应漏洞：

- 管理员初始化有明确流程。当前注册代码包含 BootstrapAdmin 路径，需要验证首次部署期间的管理员归属、并发行为和注册开放策略。
- 开发 PostgreSQL 默认仅绑定本机；生产不公开数据库端口。示例密钥由初始化命令随机生成，不提供通用管理密码。
- 本地 daemon 保留 loopback 和 Token 防护。已有 Node server-mode 作为独立运行模式说明，不把本地 daemon 直接当公网多用户服务暴露。
- 检查角色和账户隔离、MCP 授权、上游 URL/SSRF、文件路径与上传限制、Skill 安装执行边界、Electron IPC/预加载桥接及日志脱敏。
- 说明桌面会话、文件、模型输入、审计和 Agent 活动数据的流向、留存与删除方式；自托管用户应能识别哪些信息会离开本机。

沿用 Clawee 品牌及现有 `com.clawee.desktop` appId，版本提升至 1.1.0；首发以全新配置和空数据库验证。保留现有数据库迁移文件用于新部署建表，但不增加旧版本探测、配置转换、数据搬迁、双更新源或新旧协议兼容层。此决定不授权清理旧用户目录或操作旧生产数据库。

## 5. 公开用户的最小可运行路径

首版提供“自托管完整部署”：

1. 克隆一个仓库，运行初始化命令，在仓库外创建运维目录、示例配置和随机密钥。
2. 启动 PostgreSQL，执行现有迁移，启动 Gateway 和管理台。
3. 完成管理员初始化并创建普通账号，配置最小 MCP 上游和授权。
4. 启动或安装客户端，填写自己的 Gateway 地址并登录。
5. 在 `enterprise_managed` 流程中填写模型地址、模型名和密钥，完成真实任务及一次 MCP 调用。

模型调用仍需要用户提供有效模型服务，这应在 README 环境要求中写明。普通贡献者的单元测试和基本 CI 使用 mock，不要求维护者的账号或生产凭据。

无需 Gateway 的完全离线客户端可作为后续产品选项，但当前认证和模型配置已与 Gateway 耦合，不能把它当成已存在能力写入首发说明，也不将其增加为本次必要重构。

直接复用服务端已提交的配置外置化实现。最新开发文档仍以 `cd ../clawee-ops` 开头，首次使用者尚无此目录时会失败；新仓库初始化流程应先创建目录，再解析绝对路径，并验证空机器可执行。

## 6. CI、发布与维护

PR 检查不依赖生产 Secret；发布工作流使用独立受保护的 release Environment。客户端已有 CI/preflight/release 三个 workflow；服务端尚未发现已跟踪的 GitHub Actions，需要补齐。

| 层级 | 检查内容 | 验收要求 |
| --- | --- | --- |
| 公开前扫描 | 凭据、个人/客户数据、许可、依赖漏洞、产物内容 | 无未经处理的凭据；依赖发现逐项研判并处理阻断问题，扫描服务失败不能算通过 |
| 客户端 | 现有 test、typecheck、build、Runtime 合同检查、相关 E2E | 迁移后仍通过，Web/Desktop 共用界面及本地服务行为保持一致 |
| 服务端 | Go 测试、Web 测试与构建、临时 PostgreSQL 集成测试、Collector 构建 | 不依赖现有生产数据库及运维配置 |
| 跨组件 | 登录、过期/注销、Agent 绑定、模型配置、MCP 允许/拒绝、Skill、共享文件与活动上报 | 复用已有契约与 fixture，补足真实两端交互和禁用可选服务的覆盖 |
| 自托管 | 全新用户目录、空数据库、仅公共依赖下载 | 完成第 5 节全部步骤；重启、持久化和备份恢复可验证 |
| 桌面交付 | 本机预检、实际打包 App E2E、内嵌 Web 哈希校验、支持平台矩阵 | 保留现有发布门禁，不能只凭源码测试宣称可发布 |

发布流程遵守源项目现有约束：修改后的本地预检先通过；正式提交保持干净并生成关联证据，再运行该 SHA 的远端 preflight，最后通过 Tag 检查。普通 PR 与社区本地构建不应要求正式 Apple 签名凭据。此次方案阶段不运行 workflow、不创建 Tag。

首版正式 Tag 固定为 `v1.1.0`，统一发布客户端和服务端组合，并记录组件版本、API 范围和数据库初始化要求。预发布需要时使用 `v1.1.0-rc.N` 并标为 prerelease，不能进入 stable 更新源；普通开发提交不创建版本 Tag。服务端和客户端都从同一提交构建，避免独立打 Tag 意外触发桌面正式发布。

桌面使用 electron-updater 的 GitHub provider，owner 为 `krillinai`、repo 为 `Clawee`。除了安装包，发布流程必须提供平台更新元数据及对应文件和校验信息；macOS 自动更新需要 ZIP，不能只上传 DMG。验证更新元数据解析、下载和校验，fork 的开发构建默认不访问或发布上游正式更新源。现有正式平台范围保持 macOS arm64/x64、Windows x64；Linux 首发交付服务端，不新增 Linux 桌面支持承诺。

将维护者签名、公证和发布权限迁移到新仓库配置，不复制明文 Secret。外部 PR 使用只读权限，禁止通过执行不可信 PR 代码读取发布凭据。公共测试 artifact 同样应脱敏。

补齐中文 README、架构边界、开发指南、配置参考、升级与备份恢复、故障排查、贡献约定、安全漏洞私密报告方式、Issue/PR 模板和维护责任人。可采用 DCO；仅在双许可等确有需要时再评估 CLA。
