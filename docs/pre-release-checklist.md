## 已确定的状态与决策

- 整合源码已成为公开仓库 `krillinai/Clawee` 的 `main` 分支，旧私有 Git 历史未导入。
- 当前发布方案变更必须先完成本机验证。分支推送和 PR 不自动运行 workflow；客户端 CI、Server CI 和 Release Preflight 仅按需手动运行，Source Security 与正式构建发布仅由 `v*` Tag 自动触发。本机结果不能代替要求执行的远端 Release Preflight。
- 项目许可 Apache-2.0，通用能力全部开放，商业服务可选，首个整合正式版本目标 `v0.1.0`。
- 当前完成的是源码公开；本机预检通过不等于正式安装包、签名、公证、镜像和更新渠道已经发行。
- 第三方再分发许可补齐或替换属于后续专项，不阻塞源码整理和公开，也不在当前功能验收中升级依赖。
- macOS 签名、公证及其凭据由有权限的同事在前置整理完成后处理。

## 五、正式版本执行顺序

所有功能缺陷、交付范围和产物要求收敛后再执行；本清单本身不触发 workflow、创建 Tag 或发布镜像。

1. 固定最终 `v0.1.0` 版本、发布说明、已知限制和产物清单；客户端与服务端从同一 SHA 构建，说明全新部署流程，不补写旧用户迁移兼容层。
2. 对最终改动运行并通过本地 `desktop:preflight:local`，完成相关服务端和部署检查。
3. 创建本地提交，在该干净提交上运行 `pnpm run desktop:preflight:release`，验证正式签名、公证条件和打包结果；本机验证通过前不得推送。
4. 本机验证通过后将目标 SHA 推送到 `main`，确认没有分支 workflow 被自动触发，并报告本地结果、目标完整 SHA 和计划 workflow 次数。
5. 对该已推送 SHA 运行一次远端 Release Preflight。失败时先本地定位修复，新 SHA 重新形成证据，不用远端反复试错。
6. 运行 `pnpm run desktop:tag:check` 并审查结果。正式 `v0.1.0` Tag 创建后不移动、不删除重建。
7. 正式发行后核对桌面安装包、macOS 更新 ZIP、平台更新元数据、统一发布清单和校验信息；核对同一 Release 的服务端包及 `ghcr.io/krillinai/clawee-server:0.1.0`，记录镜像摘要。
8. 从发布附件完成实际下载、安装、启动和部署。验证 stable 更新元数据解析、文件下载与校验，社区开发构建仍默认不启用上游正式更新。

如需要候选版本，使用 `v0.1.0-rc.N` 并标记 prerelease。候选桌面包不写入官方稳定更新标记，候选镜像不更新 `latest`。
