# 业务知识文档规范

版本：V1.0 建议稿｜更新日期：2026-10-23

适用于公司制度、业务流程、产品资料、服务政策、操作手册、常见问答和业务经验的整理、审核与入库，供 Clawee Agent 查询使用。

整理时做到：**主题明确、条件完整、术语统一、版本有效、来源可查。** 知识库通常只返回相关片段，每个关键小节都应能独立说明业务对象、适用条件和处理规则。

## 1. 文档组织

一份文档围绕一个业务主题。出现以下情况时拆分：

- 业务对象不同，如不同产品、制度或流程。
- 负责人或更新频率不同。
- 可访问人员不同。
- 地区、渠道、客户类型或生效时间不同，容易混淆。

不要将制度、产品、销售话术和会议纪要合成一份“公司资料大全”，也不要机械地按页数拆分。完整流程可放在一份文档中，用小节划分步骤，并保留条件、分支和例外。

同一产品的规格、售后和活动政策可分别维护，每份都要写明完整产品名、型号和适用范围。

## 2. 文件格式

新整理的文字资料优先使用 Markdown。现有 Word、PDF 可转换后入库，但必须核对标题、表格、脚注和关键数字。

| 文件格式 | 整理要求 |
| --- | --- |
| Markdown `.md` | 使用 UTF-8 编码；用标准标题、段落、列表和简单表格组织内容 |
| Word `.docx` | 使用“标题 1/2/3”等样式；清理修订和批注；避免文本框、多栏排版 |
| PDF `.pdf` | 优先选择可复制文字的电子版；扫描件识别后核对文字；复杂表格补文字说明 |
| Excel `.xlsx` | 首行字段名，每行一条记录；取消合并单元格；保留对象、单位和适用范围 |
| CSV `.csv` | 使用 UTF-8 编码；首行字段名；正确处理逗号、引号和换行；明确空值含义 |
| 纯文本 `.txt` | 使用 UTF-8 编码，保留清晰的标题、段落和编号；有层级内容时优先改为 Markdown |

其他格式先整理为上述格式，不要只修改扩展名。上传限制见文末附录。

## 3. 文件命名与版本

### 3.1 文件命名

建议使用：

```text
业务域_对象或主题_文档类型_V版本号_生效日期.扩展名
```

示例：

```text
人事_国内差旅_报销制度_V1.2_2026-10-01.md
客服_A100产品_退换货规则_V2.0_2026-10-15.md
运营_经销商入驻_操作流程_V1.0_2026-10-20.md
```

不使用“最终版”“最新版2”等命名；同名但含义不同的资料，增加型号、地区或渠道。

文件名用于识别来源，不能替代正文中的业务对象和生效信息。

### 3.2 文首信息

每份文档开头填写以下信息：

| 字段 | 填写要求 |
| --- | --- |
| 文档编号 | 稳定且唯一，如 `CS-A100-RETURN`；更新版本时沿用同一编号 |
| 文档名称 | 能直接识别业务主题 |
| 业务对象及范围 | 产品或型号、组织、地区、渠道、客户类型等；不适用项写“不适用” |
| 文档状态 | 草稿、已生效、待生效、已废止；日常知识库默认仅纳入已生效资料 |
| 版本及时间 | 版本号、生效日期、失效日期或“持续有效”、最近审核日期 |
| 负责人及审核人 | 填写负责岗位或团队，以及可追溯的业务审核记录 |
| 权威来源 | 制度编号、产品规格书编号、审批记录、来源链接等 |
| 使用范围 | 如全员、客服团队、特定项目组；由维护人据此选择实际授权范围 |

待生效政策单独管理，写明“尚未生效”和开始执行的时间。

文首信息不一定出现在每条检索片段中，关键小节仍要写明必要的对象、范围和日期。文档注明“仅客服可见”后，还需由维护人配置实际访问权限。

### 3.3 现行版本与历史归档

- 同一对象、同一适用范围、同一时间段，必须有明确的权威口径；有冲突先由业务负责人确认。
- 新版通过审核和验证后，旧版应从日常检索范围移除。仅在旧版正文标注“已废止”，仍可能被召回。
- 需要历史查询时，历史资料使用独立的归档范围，并写明有效起止日期；历史问题必须带查询时间。
- 相同内容保留一份权威入库正文，避免原始 PDF、转换后的 Markdown 和重复 FAQ 同时入库；原件另行归档。
- 更新文件名或上传同名文件，不代表自动覆盖旧索引。维护人必须核实新旧文档记录和实际检索结果。

## 4. 正文写法

### 4.1 标题必须描述业务问题

Markdown 使用 `#`、`##`、`###` 表示层级；Word 使用对应的标题样式。建议一份文档一个一级标题，正文主要使用二、三级标题，避免跳级。

| 不推荐 | 推荐 |
| --- | --- |
| 说明 | A100 产品保修期与起算方式 |
| 注意事项 | 经销商入驻资料不完整时的处理 |
| 其他 | 国内差旅住宿费超标的审批要求 |
| 常见问题 | A100 产品无法开机时如何排查 |

不要用装饰符号、连续空格、居中排版或截图里的标题代替真实结构。

### 4.2 每个小节必须能独立理解

关键规则按以下顺序表达：

```text
业务对象与适用范围 → 触发条件 → 具体规则或步骤 → 例外及边界 → 处理结果
```

以下为虚构示例，仅说明写法。

不推荐：

```text
售后期限为 7 天。特殊产品除外，按上面的规定处理。
```

推荐：

```text
## A100 产品未拆封退货的申请期限

适用范围：官网零售渠道购买的 A100 产品；适用于 2026-10-01 起签收的订单。

规则：消费者自签收次日起 7 个自然日内，可以对未拆封的 A100 产品申请退货。
签收次日计为第 1 日，第 7 日 23:59 为申请截止时间，时间按北京时间计算。
商品及随附配件必须完整，申请时提供订单号。

例外：定制款不适用上述退货规则；质量问题按《A100 产品质量问题处理规则》办理。
```

引用其他规则时，相关文档必须已整理并可查询；关键条件不能只留在引用中。

### 4.3 控制主题范围，保留完整语义

- 一个小节围绕一个问题或一组紧密关联的规则；一个自然段表达一个主要意思。
- 条件、否定词、金额、比例、期限与对应结论尽量放在同一段或相邻列表中。
- 不得把“适用条件”全部放在文首，把例外放到文末，却在中间散落大量不带范围的规则。
- 不得将一个问题和答案分别放在不同章节；FAQ 的完整问答应相邻。
- 避免“同上”“如前所述”“该产品”“他们”等依赖远处上下文的说法，必要时重复完整对象名。
- 跨文档引用应写明文档名和编号，说明引用的具体事项；回答本节问题所必需的核心条件仍应在本节写明。

小节过长时按子主题拆分，不为凑字数补话，也不为缩短篇幅删掉必要条件。分段效果在入库后检查。

## 5. 不同业务资料的内容要求

| 资料类型 | 必须整理的内容 | 常见问题 |
| --- | --- | --- |
| 制度、政策 | 适用对象、生效时间、执行标准、例外、审批权限、废止或替代关系 | 只有原则，没有可执行标准；新旧政策同时存在 |
| 操作流程、SOP | 触发条件、前置条件、角色、输入材料、操作步骤、判断分支、完成标志、异常处理 | 只有流程图；没有失败或补件时的处理方式 |
| 产品、服务资料 | 唯一标识、名称及别名、型号或版本、规格、适用场景、限制、不适用场景、售后依据 | 多型号参数混写；营销描述被当成事实承诺 |
| 销售与客服知识 | 客户问题、适用条件、标准答复、依据、不可承诺事项、升级处理条件 | 话术超出产品或合同承诺；经验未经审核 |
| 计价、结算、资格规则 | 输入字段、字段定义、单位、计算公式、取整方式、边界值、例外、示例 | 公式藏在 Excel；含税与未税混用；上限边界不清 |
| 会议纪要、业务经验 | 已确认结论、决策人或审核人、适用范围、生效时间、待办与未决事项 | 将讨论、提议和个案处理当成全公司现行规则 |
| 常见问答 | 真实问题、完整答案、条件与例外、来源、适用版本 | 只有短答案；问题使用内部缩写，用户难以命中 |

会议记录、聊天记录和历史工单先提取已确认、可复用的事实与规则，注明来源后入库；讨论、提议和未决事项留在原始记录中。

分析型问题必须有相应的数据、统计口径和依据。例如回答“为什么销量上升”，不能只凭一张销售表编造原因；未经证实的原因应标注为假设。

## 6. 术语、数字、日期和业务边界

### 6.1 术语与名称

- 同一实体使用一个标准名称；第一次出现时写明常用别名或缩写，如“客户关系管理系统（CRM）”。
- 产品型号、SKU、合同编号、制度编号等精确标识必须原样保留，不能被“润色”为近似名称。
- 正文使用业务人员常用的语言，专业英文在中文后括注。
- 不要为了搜索堆砌大量同义词。不同含义的术语不得强行合并。

### 6.2 数字与日期

| 内容 | 规范写法 |
| --- | --- |
| 金额 | 写明币种、含税或未税、计价单位，如“人民币 500 元/人/晚，含税” |
| 时间期限 | 区分自然日与工作日，写明起算事件、首日是否计入、截止时点；涉及时区时明确时区 |
| 日期 | 使用 `YYYY-MM-DD`；“本月”“明年”“近期”改成可追溯的具体时间 |
| 比例 | 写明分母和计算依据，如“退款比例按订单实付金额计算，不含运费” |
| 数量与规格 | 写明单位，区分净含量、包装量、单件和整箱等口径 |
| 区间边界 | 写明是否包含边界，如“订单金额 ≥ 500 元且 < 1000 元” |
| 变化数据 | 写明统计周期、截至时间、来源和更新人，不把历史快照称为实时数据 |

同一规则在正文、表格和 FAQ 中出现时，数字、条件和生效时间必须一致。

## 7. 表格、图片与复杂文件

### 7.1 表格必须能按记录理解

每条记录都应能单独识别对象、字段和适用条件：

1. 首行直接放字段名；说明文字另放配套文档，不在表格前堆放标题行、空行。
2. 每行一条业务记录，每列一个明确字段；同一张表中的记录结构保持一致。
3. 取消合并单元格，将原来共用的产品、地区、渠道等值填入每一行。
4. 不使用嵌套表格、多层表头或依靠跨页才能理解的表头；宽表按业务主题拆分，并保留关联编号。
5. 每行写明业务对象，关键记录带上型号、地区、渠道、生效时间等区别字段。
6. 不依赖颜色、图标、批注、隐藏行列表示业务含义，应增加明确文字字段。
7. 公式产生的业务结果应导出为已核对的值，并在配套说明中写明计算口径；不要依赖知识库执行 Excel 公式。
8. 空白、0、不适用、未知必须区分，不使用含义不明的横杠。

结构示例，数值仅用于演示：

| 产品型号 | 渠道 | 地区 | 生效日期 | 标准保修期 | 起算方式 |
| --- | --- | --- | --- | --- | --- |
| A100 | 官网零售 | 中国大陆 | 2026-10-01 | 12 个月 | 按有效购买凭证记载日期起算 |
| A100 | 经销商 | 中国大陆 | 2026-10-01 | 12 个月 | 按有效购买凭证记载日期起算 |

若检索片段只有“12 个月”，没有产品、条件或字段名，应补齐记录或文字说明后重新验证。

精确求和、排名、跨表关联、全量列举和实时库存等需求，优先通过业务系统或结构化查询工具完成。文档知识库不能保证召回表格全部记录；若提供统计摘要，应先计算并复核，再注明截至时间。

### 7.2 图片与流程图必须有文字对应

- 操作截图旁写清系统名称、页面路径、操作动作和完成标志。
- 流程图转换为有序步骤，所有分支写成“如果……则……；否则……”。
- 图表补充指标、坐标含义、时间范围、关键数值与有依据的结论。
- 印章、手写批注、截图内的小字和二维码链接不能成为唯一知识来源。
- 图片与文字表达同一事实时，数值和条件必须一致。

关键知识直接写入正文，不只放在图片、网页链接或附件中；引用的内容应另行整理入库。

### 7.3 PDF、扫描件与排版清理

- 尽量从原始电子文档导出，不以截图或扫描件替代已有的可编辑文字。
- 扫描件检查页序、方向、清晰度和缺页；OCR 后重点核对金额、小数点、日期、编号以及“不”“仅”“除外”等字词。
- 清理反复出现的页眉、页脚、空白页、目录噪音和影响文字识别的装饰内容，保留必要的章节与条款编号。
- 在有权处理的入库副本中去除影响识别的水印，保留原始档案和必要的业务、权属信息。
- 转为 Markdown 后，逐项核对标题、列表、表格、脚注和关键数字。单纯“转换成功”不能替代核对。

## 8. FAQ 与检索表达

FAQ 用来覆盖真实提问方式，适合退换货条件、办理入口、材料清单、报错处理等高频问题。

- 用用户会说的话写问题，如“A100 买了以后多久可以申请退货？”。
- 答案写成完整句子，包含对象、范围、条件和例外，不能只写“7 天”。
- 必要时在同一问答下补充 1–3 个常见问法；不要大量复制同一答案制造重复切片。
- 涉及其他产品、渠道或地区时分别写明，不能用一个笼统答案覆盖。
- FAQ 与制度、规格书保持同源；变更时一起校对。若单独维护 FAQ，必须记录权威来源和对应版本。

FAQ 用于补充高频问法，制度和操作手册可保留原有结构。

## 9. 审核与入库

### 9.1 分工与交付物

| 角色 | 负责事项 |
| --- | --- |
| 业务编写人 | 整理内容、统一术语、补齐条件与例外，提供来源和测试问题 |
| 业务审核人 | 确认事实、数字、现行版本、适用范围和承诺边界 |
| 知识库维护人 | 选择知识库与授权范围，上传、跟踪状态、检查切片、清理旧版和登记结果 |

每份资料交付：入库正文、原始依据或其位置、审核记录、测试问题与预期答案。测试答案和台账另存，不作为业务知识上传。

台账记录文档编号、版本、负责人、来源、所属知识库、文档 ID、上传日期、验证结果和替代关系。

### 9.2 操作顺序

1. **盘点：**按主题、负责人、有效期和访问范围分类，找出缺失、重复和冲突。
2. **整理：**选定权威来源，补齐内容并核对格式和关键事实。
3. **审核：**业务审核人确认规则、适用范围、生效时间和替代关系。
4. **试导入：**先选有代表性的文字、表格或图文资料，确认解析结果后再批量整理。
5. **验收：**文档显示“可用”后，由维护人检查解析切片，再用实际业务账号在 Clawee 中测试问答。
6. **更新：**通过验收后移除旧版、登记台账；更新资料时重复审核和验证。

### 9.3 权限与数据范围

不同可见范围的资料放入分别授权的知识库。文件名或正文中的“内部”“仅管理层可见”等标注不能代替系统权限。

入库前移除与问答无关的个人敏感信息、账号密钥等内容；需要业务样例时使用经批准的样例或脱敏数据。

## 10. 检查与维护

### 10.1 入库前检查清单

- [ ] 文件属于当前支持的格式，非空且未超过上传限制。
- [ ] 已指定业务负责人、审核人和权威来源。
- [ ] 文档编号、版本、状态、生效时间与适用范围齐全。
- [ ] 标题有真实层级，名称能识别业务对象。
- [ ] 关键规则的小节独立可理解，条件、结果、例外相邻。
- [ ] 金额、比例、期限、型号、编号等已与原始依据核对。
- [ ] 术语、别名和日期口径统一，正文与表格没有冲突。
- [ ] 表格已取消合并单元格，每条记录带必要的对象与范围字段。
- [ ] 截图、流程图和扫描内容已有经核对的文字说明。
- [ ] 已确定知识库及访问范围，排除无关敏感信息。
- [ ] 已确定旧版处理方式，避免重复或冲突入库。
- [ ] 已准备测试问题、预期答案及出处。

### 10.2 入库后检查清单

每份文档抽检开头、中间、结尾及一处复杂内容；关键规则、金额、期限、否定条件和例外逐项核对。短文档检查全文。

- [ ] 文档在 Clawee 中显示为“可用”。
- [ ] 解析内容没有缺页、乱码、异常符号或明显错序。
- [ ] 标题和正文关系正确，表格记录没有丢失表头或对象。
- [ ] 关键规则没有被截断为改变含义的片段，尤其检查“不”“仅”“除外”等。
- [ ] 主要业务问法能检索到包含正确依据的片段。
- [ ] Agent 的回答与依据一致，没有遗漏影响结论的条件。
- [ ] 来源能追溯到目标文档，且版本、地区、渠道等匹配。
- [ ] 已使用目标业务账号验证权限，新版更新后旧口径不再进入日常查询结果。

### 10.3 测试问题与通过标准

每份文档建议至少准备 1~3 条测试，覆盖直接事实、口语或别名、条件或例外、时间或版本，以及资料未覆盖的问题；涉及多产品或渠道时增加比较测试。预期答案来自已审核资料。

单篇测试逐步汇入知识库评测集，覆盖事实查询、比较、操作指导和分析问题。每次更新后用同一套问题复测，并补入实际使用中答错的问题。

每条用例至少记录：问题、期望的适用对象和版本、预期答案要点、依据文档及章节、实际返回片段、实际答案、是否通过、失败原因。比较结果时保持账号权限、知识库范围、查询方式与召回数量等条件一致，并记录实际检索词。

建议按以下标准验收：

| 检查项 | 通过标准 |
| --- | --- |
| 关键业务规则 | 金额、期限、资格、审批、合同或售后承诺等关键测试全部通过 |
| 普通有答案问题 | 正确依据命中率不低于 90%；每条失败都记录原因和处理安排 |
| 资料未覆盖的问题 | 明确说明现有资料不足，不得把推测当作公司正式规则 |
| 版本与范围 | 不得把旧版、其他型号或其他地区规则误作当前规则 |
| 来源与权限 | 依据可追溯；不应返回无权访问的知识库内容 |

正确依据命中率＝返回片段中包含完整、正确且适用依据的有答案问题数 ÷ 有答案问题总数。需要多份依据时须全部覆盖；最终答案也要单独核对。

### 10.4 按问题位置修复

| 现象 | 优先检查 | 处理方式 |
| --- | --- | --- |
| 原文没有答案 | 知识缺失 | 由业务补充并审核，不能只调整参数 |
| 原文有，解析后没有 | OCR、版式、表格、图片 | 清理格式、补文字或换用更稳定的入库格式 |
| 解析完整，切片缺上下文 | 条件与规则分离、小节过长 | 调整源文档结构，必要时由管理员处理切片策略 |
| 切片正确，检索未命中 | 名称、别名、范围、查询表达 | 统一术语、补充真实问法，结合实际链路检查检索配置 |
| 命中别的产品或旧版本 | 对象不清、重复、旧版未退出 | 补齐对象字段、清理冲突，核对当前可用的过滤方式 |
| 正确片段已返回，答案仍错 | Agent 理解、提示词、上下文 | 检查回答生成环节，避免无依据地继续改写事实 |

流程、政策、产品状态或法规变化时及时更新。建议高频变动资料每月复核，稳定资料每季度复核，并登记最近审核日期。

## 附录：使用限制

### 使用限制

- Clawee 当前支持 `.pdf`、`.docx`、`.md`、`.txt`、`.xlsx`、`.csv`，文件非空，单文件不超过 **50 MiB（52,428,800 字节）**。
- 表格和纯文本建议控制在 10 MB 以内，表格建议在 10 万行以内；大文件优先按业务主题拆分。文件还须满足当前百炼服务的限制。
- 分段长度和检索参数由知识库维护人处理。业务人员按主题和语义组织内容，不需要按 token 数拆文档。
- 在管理入口修正了检索切片时，同步修正源文档；重新导入后再次验证。
- 业务正文及其解析、索引内容会交由配置的阿里云百炼服务处理，按公司允许上云的范围准备资料。
