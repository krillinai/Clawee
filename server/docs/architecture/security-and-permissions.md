# 安全与权限

## 身份边界

系统区分三类调用主体：

- 用户或管理员通过账号 Session 访问 Web 和 HTTP API。
- Clawee Agent 使用绑定到稳定 `agent_id` 的应用令牌访问 `/api/v1/app/*`。
- MCP Client 使用账户或 Agent 的 MCP 凭据访问 `/mcp*`。

客户端提交的账户 ID、Agent ID、角色或权限都不能直接作为授权依据。服务端必须从已验证的 Session、令牌和数据库关系中恢复主体。

## 管理台 RBAC

管理 API 位于 `/api/v1/admin/*`。权限按模块区分 `read` 与 `manage`，目前覆盖：

- 账号、角色与权限；
- Agent 与 Collector；
- MCP 上游、能力、授权、门禁和审计；
- Agent 活动、知识库、Skill、共享文件和数据资源授权。

`manage` 权限包含同模块的 `read` 权限。高权限操作仍应在服务层再次校验目标资源和业务约束。

## Agent 能力授权

MCP 能力采用显式 Grant：

1. 上游服务同步产生能力目录。
2. 管理员将具体能力授权给具体 Agent。
3. Agent 只能发现和调用当前仍有效的能力。
4. 上游、能力、Agent 或 Grant 被停用后，后续调用立即失效。

能力列表只用于展示和发现。工具调用前必须重新读取授权状态，不能把客户端曾经看到某个工具视为持续授权。

## 用户确认与管理员审批

门禁分为两类：

- **用户确认**：由实际发起调用的用户确认参数和风险。
- **管理员审批**：由具有门禁管理权限的管理员决定是否允许执行。

当能力策略同时要求两类门禁时，系统先完成管理员审批，再完成用户确认。Gate 保存能力版本、参数摘要和参数快照；确认后若能力 Schema 或原始参数发生变化，调用应被拒绝并重新发起。

## 数据资源权限

知识库、Skill 空间和共享文件等资源使用账户级数据权限。无权访问时，接口应避免通过错误差异泄露资源是否存在。Agent 的 MCP Grant 与账户的数据权限属于不同维度，两者不能相互替代。

## 审计

MCP 调用审计至少关联：

- 请求主体、Agent 和目标 endpoint；
- 上游服务、能力和版本；
- Grant 与门禁决策；
- 请求状态、执行结果、耗时和错误类别。

审计和普通日志不得记录明文密码、Bearer Token、OAuth Secret、上游凭据或上传文件正文。需要排障时优先记录不可逆指纹、内部标识和结构化错误码。

## 部署要求

- 生产环境必须使用 HTTPS，并启用 Secure Cookie。
- JWT 签名密钥和 Agent Token 加密密钥必须独立生成并放在 Secret 管理系统中。
- OAuth 回调地址必须使用明确允许的绝对 URL。
- `/metrics`、性能分析和管理接口应由网络策略限制访问范围。
- 数据库、文件目录、发布产物和备份应采用最小权限账户。
